# 01 总体架构与 DLP 能力地图

> 上级：[README](./README.md) ｜ 相关：[02 内核架构](./02-kernel-architecture.md)、[03 异步裁决](./03-async-adjudication.md)

## 现状

当前是「文件/网络访问控制」形态：内核两个 provider（MiniFilter + WFP）做元数据匹配与阻断，用户态 Electron + N-API 负责 UI 与事件展示。**尚不具备内容感知（DLP 灵魂）**。

## 目标

演进为**端侧为主的内容感知型 DLP**，架构上预留中心化（Agent-Server）。核心是把「重内容检测」上移用户态，内核通过异步裁决支撑深度判定。

## 内核 / 用户态职责边界（关键）

| 职责 | 归属 | 说明 |
|---|---|---|
| 拦截点、IO 挂起(pend) | 内核 | MiniFilter / WFP callout |
| 内容抓取（样本、头部、body 片段）| 内核 | 只抓不深析 |
| 轻量判定（扩展名/端口/卷类型/命中缓存）| 内核 | 快路径，避免每 IO 跨态 |
| 深度内容检测（正则/指纹/类型/OCR/ML）| **用户态** | 重逻辑，绝不入内核 |
| 最终策略决策（分类矩阵）| 用户态 | 可结合身份/分类/上下文 |
| 剪贴板/截屏/打印采集 | 用户态 | 内核做不到 |
| 可靠上报/审计/取证 | 用户态 | 持久化、续传 |
| 中心化通信 | 用户态（预留）| Agent-Server |

> **重要结论**：通道 provider **横跨内核与用户态**——文件/网络/USB 在内核，剪贴板/截屏/打印在用户态。因此 Core 的策略/检测/上报接口必须同时服务两侧 provider。详见 [04](./04-data-channels.md)。
