# 两阶段线路删除设计

## 目标

删除控制面线路记录之前，必须先清理 Entry、Relay、Exit 的实例配置并确认控制 socket 和端口释放。草稿、失败开线、活动线路使用同一清理流程。

## 正常删除

带规格的线路执行 DELETE 时不直接删除数据库。控制面保存删除请求并创建带 `delete_after_cleanup=true` 的 `line.disable` 任务，线路进入 `deleting` 状态。Worker 使用 operation plan 在三端执行实例级 `deploy.py stop`，删除两个 worker 配置并 reload shard。

Worker 必须确认三端配置文件和控制 socket 均消失，再完整扫描三端端口并替换运行时声明。确认目标 `instance_id` 不再出现在声明中后，Worker提交成功结果。控制面随后写删除审计，并删除线路、规格、任务、事件、告警和遥测记录。

## 失败与重试

任一节点清理或回读失败时，`line.disable` 任务失败，线路和删除请求继续保留，不执行数据库删除。再次点击删除可创建新的清理任务。已经清理成功的节点允许幂等重复清理。

## 强制删除

仅当节点不可达、异常或已有失败停用任务时允许强制删除。强制删除只清理控制面记录，运行时端口声明继续保留；前端明确显示可能存在 orphan，直到 Worker 后续完整扫描确认配置不存在才释放。

## 兼容性

没有规格或节点的纯空草稿可以直接删除。普通 `line.disable` 仍只把线路标记为 disabled，不触发删除。现有动态 Worker 继续使用 `line.disable` 权限，无需新增操作白名单。

## 验收

- 删除草稿或失败开线时先出现清理任务，线路记录仍存在。
- 三端配置和 socket 消失且端口声明刷新后，线路记录才消失。
- 清理失败时线路不消失。
- 强制删除保留 orphan 端口声明。
- 当前已删除线路遗留的节点配置可按实例精确清理，保留 `gz-hk-kz-00012_1`。
