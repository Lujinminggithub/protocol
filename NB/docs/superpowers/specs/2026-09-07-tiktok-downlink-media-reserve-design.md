# TikTok 下行媒体保护与租户带宽保底设计

## 目标

修复明确 TikTok 视频 CDN 被运行时降为 Bulk、逻辑流下行交付未进入 Entry 流量指标，以及同一租户内 Bulk 先消耗全部令牌导致媒体无法及时读取的问题。

## 分流边界

沿用 `sing-box-extern` 的明确用途优先原则：控制、可信媒体、明确 Bulk 分开处理，不能以宽泛的 `tiktokcdn` 或 `cdn` 关键字提升整类流量。NB 已有生产证据确认 `teko*` 承载观看视频，因此将 `teko*` 加入可信媒体不可降级集合。未知 CDN 和 `odr.itunes.apple.com` 继续保持 Bulk。

可信媒体规则不得触发 `NB_LIVE_FLOW_DEMOTE_DOWNLINK`。动态晋升得到的媒体仍可按现有连续窗口回落，避免普通大下载永久占用媒体优先级。

## 逻辑流计量

逻辑流只在数据实际写入本地 TCP 目标后计量：Entry 本地交付计入 `bytes_s2c`，Exit 本地交付计入 `bytes_c2s`。重放、重复帧和仅进入 `q2t` 尚未写出的数据不得提前计量。现有 `logical_rx_delivered`、确认偏移和重连语义保持不变。

## 租户媒体保底

现有每租户、每方向总令牌桶继续作为产品带宽上限。新增共享媒体活动期限和媒体储备：

- 媒体读取请求将对应方向标记为活跃 3 秒。
- 储备量为该方向 250ms 产品速率对应字节数，且不超过配置突发额度。
- 媒体可使用全部可用令牌。
- 媒体活跃期间，Bulk 只能使用总令牌中超过储备量的部分。
- 没有媒体需求时，Bulk 仍能持续使用全部产品速率；储备只保留突发信用，不固定切走带宽。
- 本地和多 worker 共享租户状态必须使用同一算法，共享状态版本递增并在部署时安全重建。

UDP/TCP 均按当前流分类调用新接口。只有仍为 Media 的流使用储备；已明确或动态降为 Bulk 的流不使用储备。

## 可观测性与兼容性

保留现有租户配置格式和 `nb_tenant_take` API；新增按媒体属性取令牌的 API，旧调用保持原语义。线路上下行限速仍为配置值，不提高套餐带宽。Entry 图表应在逻辑流实际交付后显示下行字节。

## 验证与回滚

单元测试覆盖 `teko*` 不降级、普通动态媒体仍可降级、逻辑交付方向计数、本地及共享令牌桶的媒体储备、媒体空闲后 Bulk 恢复。集成验证同时运行 3.4Mbps 媒体和高负载 Bulk，要求媒体达到目标、Bulk 使用剩余额度、总量不长期超过套餐限速，Entry/Middle/Exit 下行计数方向一致。

部署前记录当前 release。部署后若健康门禁、单流 5Mbps 双向完整性或并发媒体保底任一失败，恢复原 release。

共享状态布局升级期间不得滚动混跑旧、新 worker。每个角色必须先同时停止全部 worker，再统一启动新版本；回滚时也按同样方式成组切换。
