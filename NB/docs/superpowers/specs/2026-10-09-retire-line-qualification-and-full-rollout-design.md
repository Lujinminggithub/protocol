# 退役线路资格门禁与全线路升级设计

## 目标

消除已经失去数据来源的“全双工资格”产品状态，使线路管理只展示真实运行状态与独立的生产治理问题；随后通过 Web 版本升级入口构建当前源码候选，并滚动替换全部运行中线路的共享 Node 运行时。

## 已确认根因

- 当前 7 条运行中线路均没有 `line_qualifications` 记录。
- 资格门禁仍要求当前 deployment/profile 具有 90 秒、双向达到目标 95% 的主动探针证据。
- 现行规格已经要求开线与协议调优完成后清理主动探针，因此资格门禁无法由正常业务流程持续满足。
- 西班牙生产线路使用 `gz-55` 和 `HK-151`，两台设备当前被分类为测试设备，因此触发 `maintenance_required`；两台设备均为 `ready/healthy`。
- 当前成功的历史 Node release 不包含 `platform_release`，无法直接用于新版 Web 平台升级事务。

## 产品行为

### 线路管理

- 从线路列表移除“全双工资格”列。
- 从线路状态筛选中移除 `qualification_pending` 和 `qualification_failed`。
- 从线路详情移除“全双工资格”区块。
- 保持线路自身状态、环境、拓扑、上行/下行、接入端口、Profile 和操作入口不变。
- 流量分析总览、Entry、Middle、Exit 图表和证据时间轴保持不变。

### 生产治理

- `AuditProductionLines` 不再读取资格记录，也不再产生 `qualification_required`。
- `maintenance_required` 继续表示生产线路引用非生产设备，不能通过隐藏 UI 消除。
- 历史 `line_qualifications` 表和读取 API 保留，避免破坏历史数据和旧客户端兼容。

### 客户端交付

- 生产线路客户端配置要求线路处于 `active`。
- 仍拒绝存在真实生产治理 finding 的线路。
- 不再要求当前 deployment 具有 admitted qualification。
- 测试线路行为保持不变。

## 设备分类修复

- 通过 Web 设备编辑入口将 `gz-55`、`HK-151` 从测试改为生产。
- 不修改设备地址、凭据、主机密钥、管理状态或运行进程。
- 测试线路允许引用生产设备，因此 `gz-hk-us-00001` 不需要改为生产线路。
- 修改后西班牙生产线路不再产生 `maintenance_required`。

## 平台候选与全线路升级

- 使用当前已提交的 `E:\code\Newbility` Git 仓库，通过 Web“上传源码并构建候选”入口创建平台候选。
- 候选必须在控制面服务器构建 Web、Worker、Upgrader 和 Node，并保存不可变 manifest。
- 使用 Web 升级预览计算共享运行时传递闭包，不按线路重复替换共享设备角色。
- 当前运行中线路预期形成两个升级单元：
  - 单元一：`gz-hk-sp-00001`、`gz-hk-us-00001`。
  - 单元二：`gz-hk-uk-10002`、`gz-hk-us-10001`、`gz-hk-us-10002`、`gz-hk-us-10003`、`gz-hk-us-10004`。
- 两个单元顺序执行；第一单元成功并验证后才启动第二单元。
- 每个设备角色执行备份、原子替换、重启、健康检查和失败回滚；共享设备角色在单个升级单元内只替换一次。

## 验证

- 新增失败测试证明治理不再产生 `qualification_required`，但仍报告环境不匹配。
- 新增失败测试证明 active 生产线路无需资格记录即可交付客户端配置，但真实治理问题仍阻断。
- 资产测试证明全双工资格列、详情和筛选已移除，流量分析资产保持。
- 运行 Go 全量、Worker/Upgrader race、关键 Python 编排测试和 CTest。
- 两仓库逐文件 SHA-256 同步后分别中文提交，不推送。
- 控制面发布后检查服务、执行器心跳、页面资源和遥测连续性。
- Web 候选构建与两个平台升级任务必须保存操作证据；升级后核对 7 条线路均运行、节点版本一致、无残留升级任务。

## 不在范围内

- 不删除历史资格表或历史资格证据。
- 不更改 NB wire format。
- 不修改流量采集、图表或事件时间轴。
- 不重新引入主动探针。
- 不将测试线路自动改为生产线路。
