# 共享节点运行时隔离、资源组兼容与英国线路恢复设计

## 背景与现场证据

控制面当前使用共享 shard 进程承载同一物理设备上的多条线路。广州设备 `gz-173` 和香港设备
`HK-103.14.33.54` 已承载 `gz-hk-us-10001` 至 `gz-hk-us-10004` 四条生产线路，英国线路
`gz-hk-uk-10001` 和 `gz-hk-uk-10002` 复用相同 Entry、Relay，仅 Exit 不同。

现场存在三个已确认问题：

1. `gz-hk-uk-10001` 的 `resource_group` 从 `gz-hk-primary` 改为
   `gz-hk-primary-product` 后，`line.open` 和两次 `line.disable` 均在 worker prepare 阶段失败。
   动态 worker 注册表只允许 `gz-hk-primary`，因此任务未进入节点。
2. `gz-hk-uk-10002` 已通过资源组检查，但在 Relay 向英国 Exit `86.53.60.2:22` 传输版本时，
   连续收到 SSH 握手重置。Exit 的有效配置仍为 `LoginGraceTime 120`、
   `MaxStartups 10:30:100`、`PerSourceMaxStartups none`，现场存在持续的分布式 SSH 扫描。
3. 现有正常开线会按 `instance_id` 写入独立配置并 reload shard，不会覆盖其他线路配置；但是
   共享二进制发生变化时会重启整个角色的 shard，失败回滚也会重启整个 shard。这两个路径会扩大
   到共享同一 Entry 或 Relay 的所有生产线路，不满足线路隔离要求。

## 目标

- 开线、停用、删除和失败回滚只修改目标线路的实例资源，不切换或重启共享运行时。
- Node 二进制激活成为独立的节点运行时维护操作，显式展示并保护全部受影响线路。
- `resource_group` 改名不再导致动态线路任务、快照或运行时端口扫描失效。
- 保留历史数据库、旧 API、静态 worker 清单和历史任务的读取兼容。
- 恢复英国线路：清理废弃的 `gz-hk-uk-10001`，完成 `gz-hk-uk-10002` 开线。
- NB wire format、现有客户端配置和线上 Node 数据面协议保持不变。

## 非目标

- 不把共享 shard 重构为每线路一个 systemd 进程。
- 不迁移或批量重写历史 `resource_group` 值。
- 不在本次工作中自动升级现有美国线路的 Node 二进制。
- 不通过跳过主机密钥、关闭 SSH 安全检查或控制面直传 Exit 规避链路问题。

## 决策一：资源组降级为兼容元数据

`resource_group` 保留在数据库、JSON 模型和历史任务中，但不再是动态任务授权、执行器选路、
并发锁、动态快照或运行时端口扫描的依据。

- Web 开线表单移除资源组输入框。
- 服务端在新线路未提供资源组时写入稳定内部值 `managed`；旧 API 仍可提交合法的历史值。
- 动态 worker 不再使用 `dynamic.resource_groups` 拒绝计划或过滤计划。
- `dynamic.resource_groups` 配置字段继续解析，保证旧配置可直接启动，但标记为兼容字段。
- 动态任务能否执行由任务类型、实际 `device_id + role`、设备凭据、主机密钥、端口范围和节点状态决定。
- 并发锁继续使用实际 `device_id + role`。同一物理设备同一角色上的变更任务串行。
- 中央端口分配和冲突检查继续按实际设备和角色执行。
- 静态 registry 中的历史线路仍保留原资源组命名空间行为，不改变旧部署的启动语义。

该方案消除人工字符串与 worker 本地白名单之间的双写一致性问题，同时避免不必要的数据迁移。

## 决策二：开线只管理线路实例

共享节点上的运行时分成两层：

1. 节点运行时层：共享 `nb_node`、`nb-<role>-shard@.service`、全局 shard 进程和共享运行时版本。
2. 线路实例层：`/etc/NB/instances/<instance_id>`、每线路证书、用户、租户、路由、白名单、
   shard 配置和控制 socket。

`line.open`、`line.disable`、线路删除和开线失败回滚只能操作第二层。无论当前活跃会话是否为零，
开线都不得执行以下动作：

- 切换 `/etc/NB/shards/nb_node`；
- 覆盖共享 shard systemd unit；
- restart 或 stop 共享 shard service；
- 回滚共享二进制链接或共享 unit。

开线不构建、不分发、不激活候选 Node 二进制，只下发目标线路的安全材料、规则、路由和实例配置，
并使用节点当前已激活的共享二进制启动新实例。若节点尚未初始化共享运行时，或者当前运行时缺少所需
能力，开线在写入实例配置前失败，并明确提示先执行节点运行时部署或升级，不在开线任务中隐式安装。

线路配置采用候选文件流程：先生成候选配置并验证完整端口注册表，再原子写入目标
`<instance_id>.conf`，发送 reload，最后只检查新实例的控制 socket 和健康状态。shard reconciliation
已经按配置 fingerprint 保留未变化的实例；新增失败时删除候选线路配置并再次 reload，既有实例不重启。

## 决策三：Node 二进制独立管理

新增或补全显式的节点运行时部署操作，按 `device_id + role` 管理共享二进制。操作创建前必须列出该
设备角色关联的全部活动线路，形成可审计的影响清单。

节点运行时升级流程为：

1. 构建并校验不可变 Node release。
2. 分发并校验目标节点上的候选二进制。
3. 阻止该设备角色接收新的线路变更和新会话。
4. 等待全部关联线路会话排空；超时则退出，不切换版本。
5. 原子切换共享二进制并只重启目标设备角色的 shard。
6. 校验所有线路控制 socket、实例数量、版本 hash 和端到端健康状态。
7. 任一门禁失败则回滚共享版本，并再次验证全部关联线路。

普通开线不自动触发上述维护操作，也不预分发候选二进制。这样“新增一个 Exit”与“升级广州或香港
共享 Node”成为两个明确、可分别审计和重试的业务动作。

## 决策四：失败、删除与并发语义

- 开线按 Exit、Relay、Entry 激活线路实例，失败时按相反顺序只撤销本次创建或修改的实例配置。
- 回滚记录每个角色的配置文件是否原先存在；不得恢复不属于目标线路的文件。
- 删除只移除目标 `instance_id` 的配置和控制 socket，reload 后确认该实例消失且其他实例仍健康。
- 共享任一实际设备角色的线路变更继续串行，不同物理设备上的任务允许有界并行。
- 共享运行时升级持有设备角色独占维护锁，并阻止同设备相关的开线、删除、验证和调优进入激活阶段。
- 资源组不参与锁键计算，也不能通过改名绕过设备冲突检查。

## 英国线路恢复

### `gz-hk-uk-10001`

该线路保持 `draft`，没有活动 deployment，且操作者已经连续两次请求删除。资源组修复部署后重新发起
正常删除，worker 应完成幂等的三角色实例清理和运行时端口确认，然后由控制面删除线路记录。远端实际
不存在该实例时视为清理成功。

### `gz-hk-uk-10002`

该线路是当前需要恢复的英国线路。先对英国 Exit 写入独立 sshd drop-in：

```text
LoginGraceTime 30
MaxStartups 50:30:200
PerSourceMaxStartups 3
```

执行 `sshd -t` 后 reload SSH，不重启主机。随后从 Relay 连续执行 SSH 握手探测，确认不再出现
`Exceeded MaxStartups`、banner reset 或 connection reset，再重试 `line.open`。重试必须复用广州、
香港当前共享二进制，只新增 `gz-hk-uk-10002_1` 的线路实例配置。

英国线路成功门禁包括：

- Entry SOCKS、Relay 和 Exit 端口与现有线路不冲突；
- 英国 Exit 绑定地址 `86.53.60.118` 生效；
- 三角色控制 socket 和实例健康正常；
- 客户端配置生成成功；
- 既有四条美国线路在开线前后均可用；
- 广州和香港 shard 主进程 PID、共享二进制 hash 不变。

## 错误处理与可观测性

- 资源组不再产生 prepare 拒绝；历史字段仅在任务详情中作为兼容信息展示。
- 节点运行时未准备时返回独立错误阶段 `runtime-preflight`，不得伪装成端口或 SSH 错误。
- 每个实例配置动作记录 `created`、`updated`、`reloaded`、`healthy` 或 `rolled-back`。
- 共享运行时操作记录受影响线路、排空数量、切换前后 hash、重启结果和逐线路 readback。
- SSH 分发失败保留每次目标地址、尝试次数和握手阶段；不输出密码或临时私钥。
- 删除结果必须区分“实例已不存在”和“节点不可达导致残留未知”。

## 测试与验收

### 自动化测试

1. 动态计划使用任意合法历史资源组时，开线、停用、快照和端口扫描均不被过滤。
2. 新线路省略资源组时由服务端写入 `managed`，旧值往返读取不变。
3. Web 不再提交人工资源组，生产/测试仍使用独立 `environment` 字段。
4. 共享运行时已存在且控制面存在候选二进制时，开线不分发候选版本、不切换 symlink、不写共享
   unit、不 restart shard。
5. 共享运行时缺失或能力不足时，开线在写配置前失败并提示独立维护操作。
6. 第二条共享 Entry/Relay 线路成功加入时，第一条线路配置、控制 socket 和 shard PID 不变。
7. Exit 激活失败时，仅撤销第二条线路配置，第一条线路继续工作。
8. 删除一条共享线路时，只移除该实例，其他实例和 shard 继续工作。
9. 节点运行时升级正确计算全部受影响线路，未排空时拒绝切换，成功和回滚均完成逐线路 readback。
10. Go 全量测试、worker race test、Python 部署测试和 Node shard 测试通过。

### 生产验收

1. 部署控制面和 worker，确认旧 registry 无需修改即可启动。
2. 记录四条美国线路健康状态、广州和香港 shard PID、共享二进制 hash。
3. 完成英国 Exit SSH 容量修复并从 Relay 做连续握手探测。
4. 删除 `gz-hk-uk-10001`，确认无远端残留和控制面记录。
5. 重试 `gz-hk-uk-10002` 开线并完成端到端验证。
6. 对比美国线路健康、共享 PID 和 hash，必须全部保持不变。
7. 将相同代码同步到 `E:\project\protocol\NB`，提交中文备注，不推送。

## 回滚

控制面发布前备份 Web、worker 二进制和 worker registry。应用回滚只恢复控制面二进制和代码，不修改
任何 Node 线路实例。英国 SSH drop-in 独立备份；若配置校验或 reload 失败，恢复原文件并保持当前
sshd 进程。任何生产验收失败立即停止后续开线，不执行共享 Node 二进制切换。
