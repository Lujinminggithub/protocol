## 4. P0 执行顺序

### P0-A 发布安全

1. 构建后生成 `build/release-manifest.json`，绑定二进制、构建输入、拓扑和线路 profile。
2. 节点使用 `/etc/NB/releases/<release_id>/nb_node` 保存不可变版本，`/etc/NB/nb_node` 仅作为原子 symlink。
3. 三节点全部预上传并校验成功后才允许开始重启。
4. 每个角色重启后校验 systemd、实际二进制哈希、worker 数和 control socket `health`。
5. 任一角色或端到端 SOCKS 冒烟失败，按 entry→middle→exit 逆序恢复上一版本。
6. code release ID 与 configuration digest 组成不可变 `deployment_id`，相同二进制的 canary 参数不会覆盖基线。
7. 发布全程写本地和远端 JSONL 审计；成功后保留当前、上一版本及最近五个版本。

### P0-B 观测与现场保全

输出统一 JSON 指标，至少包含 release ID、配置版本、角色、worker、连接、媒体吞吐、真实队龄、背压、首包、关闭原因、effective/spurious loss、重排序、CC 状态、CPU/event-loop 和 socket drop。提供三端 UTC 对齐的 incident bundle，并设置进程退出、健康失败、媒体队龄、持续有效丢包和出口建连失败告警。

当前实现：`python tools/nb_diag.py bundle` 归档三端 deployment、systemd、进程、端口、资源、journal、内核信号、NB 日志和 worker health/metrics，并允许部分节点失败。control metrics 覆盖全流吞吐、队列、真实队龄、背压、首字节、连接结果、关闭原因、effective/spurious/timer loss、重排序、CC/cwin/pacing、事件循环、UDP syscall 错误和 Linux `SO_RXQ_OVFL` 内核接收队列丢包。`python tools/nb_observe.py` 保存累计指标差量和异常连续次数；新增的接收队列溢出会按采样增量告警，并将中央控制台对应节点标记为降级。节点不可达、健康失败、deployment/profile 混跑立即告警，其他阈值连续两个窗口后触发故障包。

### P0-C 自动开通闭环

探针只生成不可直接生效的 candidate。控制流程必须校验最小样本量和 MTU 证据，经过人工或策略审批后建立 canary；生效后从 `linkq` 和 control socket 回读实际参数。连续失败窗口触发上一签名 profile 回滚，成功后才提升新会话比例。

当前实现位于 `tools/nb_line_control.py`。candidate 必须来自主动 QUIC 探针，两个 segment 均达到 10000 包和 6 个有效窗口，并具有 QUIC MTU 证据。短时探针只允许增加保护，不得直接降低既有 CUBIC cwnd 或重排序容忍。审批和 canary bundle 使用 `NB_PROFILE_SIGNING_KEY` 做 HMAC-SHA256 签名；真实执行必须显式提供 `--execute`。canary 自动运行完整性回显和持续三跳 QUIC 负载，至少采集 6 个窗口并回读三端 profile ID/schema；负载失败、连续两次节点采集失败、其他 critical 告警或队龄 P95 超过 500ms 时，精确恢复 canary 前的不可变 deployment。验收成功后仍需显式执行 `promote`，原子提升 hosts/profile 基线。

### P0-D 降低改动半径

`nb_session.h` 和 `nb_runtime.h` 保存 session/stream 与角色装配状态；`nb_session_index` 提供 O(1) 查找；`nb_pool.h` 与 `nb_path` 分离 picoquic 池状态和纯质量评分；DNS、bridge、send、metrics 均已独立。`nb_node.c` 保留角色 I/O、picoquic callback 和 event loop 装配，当前约 3379 行。`tools/p0_gate.py` 强制模块存在、主文件不超过 3500 行且无 `picoquic_add_to_stream` 调用；远端 `build` 会执行全部 CTest 后才生成发布清单。

- 每档运行真实 SOCKS→三跳 QUIC 的前后 payload 完整性、定速负载和连续 control metrics 采样；首个失败档默认停止，最后卸载 IFB 并强制跑恢复档。
- KZ middle→exit 的无损事务档通过：10 MB 完整到达，实际命中 7690 个 QUIC 包，清理后 exit 原有 `fq_codel` 保持不变。
- KZ middle→exit 的 `1% loss + 80ms` 档未通过直播基线：实际丢弃 112/11553 包，吞吐约 3.00 Mbps（目标 4 Mbps），队龄 P95 约 1.91 秒、峰值约 4.96 秒；卸载后恢复到约 3.92 Mbps、队龄 P95 约 206ms。该结果证明恢复机制有效，但当前链路在该组合退化下不具备产品级平滑性。
- 单变量复测表明 `1% loss + 0ms delay` 可通过：实际丢弃 130/12513 包，吞吐约 3.93 Mbps，队龄 P95 约 4ms，payload 完整。delay-only 的 20/40/60ms 均通过；80ms 首轮在 256KB 完整性探针阶段超时，但同条件复测通过且吞吐约 3.94 Mbps。因此当前只能确认 `1% loss + 80ms delay` 组合档失败，不能把单次 80ms 超时直接解释为固定 RTT 临界点。

- `tools/soak_test.py` 已提供分段持续三跳负载、每段前后 payload 校验、三端 health/deployment/profile/FEC/吞吐/队龄门禁、原子检查点和失败自动 incident bundle。KZ 20 秒 smoke 已通过：10MB 完整到达、约 3.93 Mbps、队龄 P95 约 106 微秒、三端版本一致。工具闭环已完成，24 小时运行时长本身仍待单独测试窗口验收。

### 5.2 2026-07-21 P0 完整验收结论

- 修复 SSH 跳板连接泄漏后，`middle -> exit` 完整矩阵共 57 个用例，33 个通过、24 个失败；报告位于 `build/netem/kz-middle-exit-full-3x-v2.json`。loss-only 的 0/1/2/3/5/8% 共 18 轮全部通过，吞吐最低约 9.81Mbps。delay-only 到 80ms 共 12 轮全部通过，额外单向 120ms 三轮全部失败。
- `middle -> exit` 在 120ms 退化后，后续 jitter 和 reorder 用例长期沿用低效 QUIC/CC 状态，队龄 P95 多次达到 0.5 到 1.1 秒；直到 reorder=10% 才重新恢复约 9.95Mbps。结论不是“10% 重排更好”，而是池连接退化后的恢复时间不可控，必须增加连接退休和快速重建机制。
- `entry -> middle` 完整矩阵共 57 个用例，32 个通过、25 个失败；报告位于 `build/netem/kz-entry-middle-full-3x.json`。0 到 3% loss 全部通过，5% 为 2/3，8% 为 0/3。专线基础 RTT 约 4.4ms，但严重损伤后的连接状态仍可通过端到端背压和连接级拥塞状态放大，因此日志中的 entry 抖动不能直接解释为专线物理抖动。
- 两段矩阵结束后 qdisc 均恢复原始 `fq_codel`，三节点服务 active，恢复 payload 完整性通过。矩阵工具已增加资源守卫、断点续跑、场景名聚合以及 Windows 原子写重试。
- 节点故障矩阵结果：entry 真实业务恢复约 7.69 秒，通过 15 秒 SLA；middle 约 30.84 秒、exit 约 31.31 秒，均失败。共同原因是旧 QUIC 连接需要等待约 30 秒 PTO/close 才建立有效新连接。
- 下午手机验收结果为失败：推流端全程绿色，但观看端出现卡顿且画质明显下降。主媒体上行 P50 约 1.68Mbps、P95 约 1.83Mbps，说明绿色状态不能替代观看端质量验收。
- 24 小时 soak 已于 2026-07-21 启动，进程状态记录为 `build/soak/kz-24h-20260721.process.json`，增量报告为 `build/soak/kz-24h-20260721.json`。完成前 P0 不得标记为通过。
- 当前 P0 阻塞项：middle/exit 故障恢复超过 15 秒、退化连接不能在数秒内退休重建、下午观看端质量验收失败、24 小时 soak 尚未完成。FEC 继续保持 observe-only。

### 5.3 失败用例修复与复验（2026-07-21）

- 针对连续矩阵中“严重退化结束后旧 QUIC/CC 状态长期污染后续用例”，新增 `nb_pool_health` 模块。仅 latency/media 和内部探针流参与判断；真实发送队龄持续超过 750ms 达 5 秒时退休旧连接并立即预建替代连接，30 秒冷却防止重连风暴。control metrics 新增 `pool_recovery.retired/suppressed`。
- entry 与 middle 使用不同判定：entry 仅接受自身 `cwin_blocked/stream_blocked`，不能因下游 flow-control 背压或单纯队龄退休；middle 允许严重队龄兜底。该限制保证 middle 下行压力仍可传播到 entry 和编码器，不会在 entry 误杀健康专线连接。
- 曾尝试用 `picoquic_path_quality.bytes_received` 判断 ACK 停滞，但单向 sink 负载证明该字段不能可靠代表 ACK-only 进度，会误杀直播上行。该逻辑已撤回，未进入最终 deployment。
- 安全基线连续 60 秒达到 9.964Mbps，payload 完整，两段均为 load-qualified，退休计数保持 0。`middle -> exit +120ms @ 10Mbps` 三轮仍失败，说明该档本身超过当前单连接能力；但队龄峰值由旧矩阵约 13.6 秒降到约 1.2 至 3.7 秒，移除 netem 后立即恢复到 9.959Mbps，不再污染后续档位。
