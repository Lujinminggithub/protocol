## 1. 阶段目标

V1.5 的定位是：

**继续保留当前 `TCP-over-QUIC` 三跳产品形态，只做服务端、中继、控制面和规模化演进。**

它不是 V2 的阉割版，而是一个明确的中间版本，目标是：

- 把现有三跳链路做得更稳
- 把当前 `nb_node.c` 数据面做得更高效
- 把后续产品化所需的服务端底座先建好
- 不因为手机客户端和新协议设计而拖住当前主线

## 2. V1.5 明确保留的前提

V1.5 继续保留这些核心约束：

- 入口仍可由现有代理入口接入
- 数据主平面仍以 `TCP-over-QUIC` 为主
- 节点角色仍是 `entry / middle / exit`
- 中继仍按 source-route 无状态转发
- 直播优化仍建立在当前 stream 体系之上

## 3. V1.5 明确不做的内容

这些内容统一放到 V2：

- 自研手机客户端
- 以 QUIC datagram 为主的实时媒体平面
- chunk 级媒体协议
- 客户端侧 FEC
- 客户端侧 multipath
- 摆脱 `TCP-over-QUIC` 的整体产品形态

## 4. V1.5 的工作边界

### 4.1 数据面

V1.5 重点改造服务端数据面，但不改产品语义：

1. 保留当前 stream relay 模型
2. 把 QUIC 发送路径从 `add_to_stream` 迁到 `prepare_to_send`
3. 保持现有 `entry / middle / exit` 生命周期与回收逻辑
4. 保持现有多连接池策略

### 4.2 FEC

V1.5 对 FEC 的目标不是“把当前双发补完整”，而是：

1. **去掉双发**
2. 改为**纠错型 FEC**
3. 保持当前 `TCP-over-QUIC` 三跳产品形态不变
4. 只在受保护坏跳上启用 hop-local FEC
5. 做按链路质量自适应

这意味着：

- V1.5 不再以“可靠 stream 双发 + 去重”作为目标方案
- V1.5 的 FEC 是**服务端/中继侧的按跳纠错能力**
- V1.5 仍不引入完整的 V2 实时平面，但允许在受保护 hop 内部增加独立 FEC sidecar 机制

### 4.2.1 V1.5 FEC 的推荐形式

推荐采用：

- **系统码 block FEC**
- 按固定大小切片
- `k` 个原始分片 + `r` 个修复分片
- 在 `middle -> exit` 这条坏跳优先落地

推荐原则：

1. 原始业务数据仍沿当前 `TCP-over-QUIC` 主流发送
2. 修复分片不再复制整条业务 stream
3. FEC 只保护直播敏感流
4. FEC 只保护被识别为坏跳的链路段

### 4.2.2 为什么 V1.5 就要去掉双发

原因很明确：

1. 双发本质上是 2 倍带宽换毛刺掩盖，不是纠错
2. 双发会把发送、排队、ACK、恢复、日志和连接压力都一起放大
3. 在 `hk -> kz` 这种长期差线场景，双发可能进一步加重瓶颈
4. 纠错型 FEC 更符合你们当前要解决的“随机丢包 + 直播抖动”问题

### 4.3 规模化

V1.5 要开始解决“单线程不是整机终局”的问题：

1. `nb_node.c` 保持单 worker 单线程模型不变
2. 节点级引入多 worker
3. 每个 worker 独立 `picoquic_quic_t`
4. 使用 `SO_REUSEPORT` 做多核扩容

### 4.4 控制面

V1.5 可以开始做控制面，但只做服务端可落地部分：

- 路由策略
- 出口健康度
- 链路质量汇聚
- 认证接口预留
- QoS 接口预留

如果某项功能强依赖自研手机客户端，则只做协议预留，不要求本阶段闭环上线。

## 5. V1.5 具体任务清单

### 5.1 数据面性能

1. `prepare_to_send` 替换主数据发送路径
2. 明确应用层背压与 QUIC 背压边界
3. 减少不必要复制和排队
4. 为纠错型 FEC 预留发送/回收/统计接口

### 5.2 并发与扩容

1. 多 worker 进程内模型
2. `SO_REUSEPORT` 接入
3. 每 worker 独立连接池、流表、统计
4. 共享只读配置与低频控制状态

### 5.3 FEC 收尾

1. 退役当前双发方案
2. 设计并实现按跳纠错型 FEC
3. 用 `tc netem` 做可重复测试
4. 建立指标：
   - 首包延迟
   - RTT 波动
   - 卡顿次数
   - 修复成功率
   - 额外带宽占比
   - 编码/解码 CPU 开销
5. 做自适应开关和回滞

### 5.4 控制面底座

1. 路由与出口选择接口
2. 节点链路质量汇聚
3. 用户认证接口预留
4. QoS 策略接口预留

## 6. V1.5 推荐实现顺序

### 第一步：发送模型改造

- 把 stream 数据发送改到 `prepare_to_send`
- 这是最直接的性能收益点

### 第二步：FEC 补全与量化

- 去掉现有直播双发方案
- 落地纠错型 FEC 的最小实现
- 建立可重复实验环境

### 第三步：多 worker 扩容

- 引入 `SO_REUSEPORT`
- 每 worker 独立 `quic context`

### 第四步：控制面与选路

- 做最小可用的服务端控制面
- 先解决“怎么换更好线路/出口”

## 7. V1.5 与 V2 的关系

V1.5 和 V2 的关系不是替代，而是上下游：

- **V1.5**：把现有三跳 relay 做成强壮的服务端底座
- **V2**：在这个底座上，再引入手机客户端、实时平面、datagram/FEC 下沉、多路径

如果 V1.5 没把这些底座做好：

- 客户端重做也接不稳
- datagram 实时平面也没有好的中继骨架
- multipath/FEC 也缺少可靠的服务端接收端

## 8. 一句话结论

V1.5 的正确目标不是“半做 V2”，而是：

**在继续保留 `TCP-over-QUIC` 的前提下，把当前 NB 服务端与中继体系做成一个可长期承载 V2 的稳定底座。**

具体到 FEC 的协议设计与实现边界，见 [09-V1.5纠错型FEC详细设计稿](09-V1.5纠错型FEC详细设计稿.md)。
