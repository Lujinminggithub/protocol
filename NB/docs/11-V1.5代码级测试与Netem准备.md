# NB V1.5 代码级测试与 Netem 准备

> [05-路线图](05-roadmap.md) | [08-V1.5实施方案](08-V1.5实施方案.md) | [09-V1.5纠错型FEC详细设计稿](09-V1.5纠错型FEC详细设计稿.md) | [10-V1.5需求优先级](10-V1.5需求优先级.md) | 11-V1.5代码级测试与Netem准备(本篇)

## 1. 目标

在进入真实直播测试前，先完成两类准备：

1. **代码级测试**
   - 不依赖真机直播
   - 不依赖真实坏线
   - 强制打开 `V1.5 FEC sidecar`
   - 强制丢 `source/repair datagram`
   - 验证 `NACK / RETX / recover`

2. **Netem 准备**
   - 明确在哪个节点、哪块网卡注入丢包
   - 明确验证指标和观察点

## 2. 当前可用测试开关

### 2.1 FEC sidecar 开关

- `NB_FEC_V15=on`
  - 开启 V1.5 sidecar/FEC 骨架

- `NB_FEC_V15_FORCE=on`
  - 忽略 `line_bad`，强制对直播优先流启用 sidecar
  - 用于代码级测试

### 2.2 丢包测试钩子

- `NB_FEC_V15_DROP_SRC_MOD=N`
  - 每 `N` 个 `source datagram` 丢 1 个

- `NB_FEC_V15_DROP_REPAIR_MOD=N`
  - 每 `N` 个 `repair datagram` 丢 1 个

推荐起步参数：

- 只测恢复链路：
  - `NB_FEC_V15_DROP_SRC_MOD=1`
  - `NB_FEC_V15_DROP_REPAIR_MOD=0`

- 测恢复失败回退：
  - `NB_FEC_V15_DROP_SRC_MOD=1`
  - `NB_FEC_V15_DROP_REPAIR_MOD=1`

## 6. Netem 准备

### 6.1 注入位置

V1.5 第一优先只针对 `middle -> exit` 坏跳。

所以优先在：

- `middle` 发往 `exit` 的网卡
- 或 `exit` 接收来自 `middle` 的网卡

进行注入。

### 6.2 基本命令模板

查看网卡：

```bash
ip addr
tc qdisc show
```

注入轻微丢包和抖动：

```bash
tc qdisc replace dev eth0 root netem delay 80ms 20ms loss 2%
```

注入更强的直播坏线场景：

```bash
tc qdisc replace dev eth0 root netem delay 120ms 40ms loss 5%
```

清除：

```bash
tc qdisc del dev eth0 root
```

### 6.3 Netem 前置条件

进入 netem 前，先满足：

1. `NB_FEC_V15_FORCE=on` 代码级测试能拉起 sidecar
2. 强制丢包测试下，日志里能看到 `drop -> recover`
3. 强制更坏丢包测试下，日志里能看到 `NACK -> RETX`

只有这 3 条成立，再上 netem 才划算。

## 7. 测试顺序建议

按这个顺序：

1. 无丢包，验证 sidecar 启动
2. 强制丢 `source`，验证恢复
3. 强制同时丢 `source + repair`，验证 `NACK / RETX`
4. 再上 netem
5. 最后再做三跳直播测试

## 7.1 最小测试矩阵

| 编号 | 目标 | 环境变量 / 条件 | 期望关键日志 |
|---|---|---|---|
| T1 | sidecar 拉起 | `NB_FEC_V15=on` `NB_FEC_V15_FORCE=on` | `fec v1.5 start` `fec ctrl START` `fec ctrl ACK` |
| T2 | 单缺片恢复 | `NB_FEC_V15_DROP_SRC_MOD=1` | `fec test drop` `fec recover block` |
| T3 | 恢复失败触发回退 | `NB_FEC_V15_DROP_SRC_MOD=1` `NB_FEC_V15_DROP_REPAIR_MOD=1` | `fec nack` `fec retx send` `fec retx recv` |
| T4 | 正向收尾 | T3 基础上发送有限长流并关闭 | `FC:FIN` 后无永久卡住，连接正常收尾 |
| T5 | 反向收尾 | T3 基础上以回程为主的大流 | `fec retx recv` `fec v15 stat` 中 `recovered/retx_recv` 增长 |
| T6 | Netem 轻度坏线 | `delay 80ms 20ms loss 2%` | `recovered > 0`，无大面积 `teardown` |
| T7 | Netem 重度坏线 | `delay 120ms 40ms loss 5%` | `nack/retx` 明显出现，连接仍可完成 |

## 8. 一句话结论

先用**强制开关 + 内建丢包钩子**把 `V1.5 FEC sidecar` 跑通，再进 `tc netem`，最后再做直播联调。

## 9. 失败时优先排查项

### 9.1 T1 失败

现象：

- 没有 `fec v1.5 start`
- 没有 `fec ctrl START`
- 没有 `fec ctrl ACK`

优先排查：

1. `NB_FEC_V15=on` 是否真的进了 `middle/exit` 进程环境
2. `NB_FEC_V15_FORCE=on` 是否生效
3. 是否真的命中了 `prio=4` 的直播敏感流
4. `middle -> exit` 连接是否正常建立
5. `nb-middle.log` / `nb-exit.log` 是否被清空过，是否看错旧日志

### 9.2 T2 失败

现象：

- 有 `fec test drop`
- 没有 `fec recover block`

优先排查：

1. `source datagram` 是否真的在发
2. `repair datagram` 是否真的在发
3. `src_count/raw_bytes/payload_len` 是否一致
4. `exit` 是否收到了未来 block 或当前 block 全量
5. 是否触发了错误的 FIN 提前收尾

### 9.3 T3 失败

现象：

- 没有 `fec nack`
- 或有 `nack` 但没有 `retx send/recv`

优先排查：

1. 未来 block / FIN 是否真的到达，驱动了 `NACK`
2. 发端历史 block 是否还在 `fec_tx_hist` 内
3. `FC:RETX` 文本长度是否超过控制流缓冲
4. `hex -> payload` 解码是否成功
5. 补发后是否重新进入 `fec_rx_handle_symbol`
