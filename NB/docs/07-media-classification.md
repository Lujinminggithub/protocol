## 0. 三十秒速览（结论先行）

- **这个系统**：把手机上抖音/TikTok 的**直播流量**，通过我们自建的三段中转线路（三跳）送到目标服务器，目的只有一个——**让直播更低延迟、不卡顿**。
- **现状问题**：系统靠一张**写死在程序里的域名关键词表**（`MEDIA_KEYS[]`）来判断"这条流量是不是直播视频"，从而决定给不给它"加速待遇"。这张表①改一次要重新编译发布，②抖音的 CDN 域名一直变、追不上。
- **最终结论**：不用再纠结"识别是不是抖音直播"。把原本纠缠在一起的**两个决策拆开**：
  1. **要不要"双发保护"** → 改成看**线路当前丢不丢包**（丢包才需要保护），跟域名无关；
  2. **要不要"走快车道"** → 交给**客户端或入口端口**来标记，也不靠域名猜。
- **可行性**：底层的 picoquic 库**已经提供了真实丢包数据**（只是现在代码没用上，填了个 0 占位）。所以这个方案能落地，改动很小。

不懂上面在说什么？往下读，全部从头解释。

## 1. 先搞懂这个系统在做什么

### 1.1 一句话定位
我们**不生产内容**，只是一个"**中转搬运工**"：把用户手机里抖音 App 产生的网络流量，接过来，通过我们自己搭的一条**跨国线路**转发出去，让直播看得更顺。用户挂这个代理，就是为了看抖音直播不卡。

### 1.2 三个角色（配类比）
这条线路由一个程序 `nb_node` 扮演三种角色串起来（代码里靠启动参数 `-r` 选角色）：

```
 手机(抖音App)
     │  TCP
     ▼
 ┌────────┐   QUIC    ┌────────┐   QUIC    ┌────────┐   TCP    目标服务器
 │ entry  │ ────────▶ │ middle │ ────────▶ │  exit  │ ──────▶ (抖音CDN)
 │ 入口   │           │ 中转   │           │ 出口   │
 └────────┘           └────────┘           └────────┘
  广州(gz)             香港(hk)             哈萨克(kz)
```

| 角色 | 通俗解释 | 类比 |
|---|---|---|
| **entry（入口）** | 离用户最近。手机的流量先到这里。它认得用户想访问哪个网站（域名） | 快递的**揽收网点** |
| **middle（中转）** | 中间跳板，负责把包裹往下一站传。**它不记账、不存状态**（"无状态"） | 中途的**转运中心** |
| **exit（出口）** | 最后一站，真正去连抖音的服务器，把数据取回来 | 最终的**派送网点** |

> **为什么要三跳这么绕？** 因为跨国网络里，直连往往丢包严重、慢；拆成几段、每段选好线路，整体更稳。这是"卖线路"类产品的常见做法。

### 1.3 一次直播的数据旅程
1. 手机抖音要看某直播，通过 **SOCKS5 协议**（一种"帮我连到某某网站"的标准代理协议）告诉 entry：「帮我连 `pull-flv-xxx.douyincdn.com` 的 1935 端口」。
2. entry 把这个目标地址写成一行**路由说明**（叫 **source-route**，形如 `T:目标host:端口`），塞进数据开头，发给 middle。
3. middle 照着路由说明连下一跳，把数据继续往 exit 传。
4. exit 真正连上抖音服务器，把直播数据取回来，原路返回手机。

### 术语速查（先扫一眼，后面遇到再回来查）
| 词 | 大白话 |
|---|---|
| **QUIC** | 一种比传统 TCP 更快的网络传输协议（基于 UDP）。我们三跳之间用它 |
| **TCP / UDP** | 两种最基础的网络传输方式。TCP 可靠但有时慢，UDP 快但不保证送达 |
| **SOCKS5** | 手机 App 对代理说"帮我连 X"的标准协议。只管连 TCP |
| **source-route** | 我们塞在数据头部的"路由说明书"，告诉每一跳下一步连谁 |
| **丢包** | 数据包在网络里弄丢了，要重发，重发就产生延迟 |
| **RTT** | 数据来回一趟的时间（毫秒）。越小越快 |
| **抖动(jitter)** | RTT 忽大忽小的程度。直播最怕这个，会一顿一顿 |
| **FEC 双发** | 把同一份数据**同时走两条线**发，任一条到了就行，用来对抗丢包（下文详解） |
| **cwnd** | 拥塞窗口，粗略理解为"这条线当前允许一次发多少数据" |

## 2. 为什么要"分流"

### 2.1 直播到底怕什么
直播卡顿（画面转圈、变黄变红）主要两个根源：
1. **丢包毛刺**：跨国线路某一跳丢了个包，QUIC 要重发，一来一回就是一个 RTT 的**卡顿尖峰**。跳数越多越明显。（我们实测：hk→kz 这段跨境线路丢包比别处高 15~20 倍，是主要瓶颈——见 [roadmap](05-roadmap.md)）
2. **抖动**：延迟忽高忽低，播放器缓冲跟不上，也会顿。

### 2.2 系统的两个"武器"
针对上面两个病，系统准备了两个武器：

**武器一：低延迟专用道（快车道）**
到下一跳其实开了 **6 条并行的 QUIC 连接**（代码：`POOL_SIZE 6`），其中**前 3 条专门留给直播/实时流量**（代码：`LAT_LANES 3`），跟"批量下载"这类大流量**物理隔开**，不让下载挤占直播。
- 直播流走快车道，标记优先级 `PRIO_LATENCY=4`；
- 普通/批量走慢车道，标记 `PRIO_BULK=20`。

**武器二：FEC 双发（双保险）**
把直播的同一份数据，**同时通过两条不同的连接各发一份**（代码里用 `flowid` 把这两条配成一对）。接收端只要**任意一条先到**就用，另一条重复的丢弃（叫"去重"）。
- 好处：某条线丢了包要重发时，**另一条很可能已经到了**，直接消除了重发的卡顿尖峰。
- 代价：**带宽翻倍**（同样的数据发了两遍），尤其吃紧张的跨国带宽。

> 一句话：**低延迟道 = 不让别人挤直播；FEC 双发 = 用双倍带宽换掉丢包卡顿。**

### 2.3 武器不能乱发 → 所以要"分流"
两个武器都有成本（快车道容量有限、双发烧带宽），**不能给所有流量都用**。比如后台下载、埋点上报这种不着急的，给它们双发就是浪费跨国带宽、还挤占直播。

于是需要**分流**：判断"这条流量是不是值得享受武器待遇"。**这就是 `MEDIA_KEYS[]` 存在的原因。**

## 3. 现在是怎么做分流的（现状与毛病）

### 3.1 两处"写死"的关键词表
代码里有两处，都是拿域名去和一张**硬编码的关键词表**做匹配：

| 位置 | 函数 | 写死的表 | 干的事 |
|---|---|---|---|
| **entry** | `classify_target()`（代码 `:251`） | `pat[]` = webcast/pull/live/flv/rtmp/rtc | 命中就给**快车道**（`PRIO_LATENCY`） |
| **middle** | `is_fec_media()`（代码 `:259`） | `MEDIA_KEYS[]` = flv/rtmp/hls/pull-/douyincdn… 共 19 个词 | 命中就**双发**（配合 `prio==PRIO_LATENCY`，代码 `:524`） |

判断方式就是最朴素的"域名里**包含**这些词吗"（`strstr` 子串匹配）。

### 3.2 写死的三个毛病
1. **改一次要重新编译发布**：关键词编进了二进制程序，加/删一个域名就得重新编译、重新部署到三台服务器。
2. **追不上抖音**：抖音直播的拉流域名带随机字符（如 `pull-flv-xxxxx`、`v3-xxx.douyinvod.com`），**一直在变**。写死的表永远慢半拍。
3. **只看得到域名、看不到路径**：`is_fec_media` 只匹配域名部分，看不到完整 URL。很多新 CDN 域名里**一个关键词都不含**，直接漏判。

### 3.3 一个更深的错误（关键！）
除了"写死"这个表面问题，还有个**判据本身用错了**的深层问题：

> **"要不要双发"这件事，根本不该由"域名是不是直播"来决定。**

想想双发的目的——**对抗丢包**。那么：
- 线路**此刻不丢包**时，就算是货真价实的抖音直播，双发也是**纯浪费带宽**（没有丢包毛刺可消）；
- 线路**此刻猛丢包**时，任何延迟敏感的流量都该被保护。

所以"要不要双发"的正确判据是**线路当前丢不丢包**，跟"这条流叫什么域名"没关系。用域名去判双发，等于**拿'流量的名字'去猜'线路的状态'**，本就是错配。

---

## 4. 核心结论：把一个问题拆成两个

前面纠结的"怎么识别抖音直播"，其实是**把两个本该分开的决策，用'是不是直播'这一个信号硬绑在了一起**。拆开看：

| 决策 | 它真正该看的东西 | 现在错用的判据 |
|---|---|---|
| **Q1：给不给快车道？**（优先级） | 这条流**急不急**（延迟敏不敏感） | 域名 `pat[]` |
| **Q2：要不要双发？**（FEC） | **线路此刻丢不丢包** | 域名 `MEDIA_KEYS[]` |

**这就是解题的钥匙**：一旦把 Q1、Q2 分开，会发现**两个都不需要靠域名去猜**——
- Q2 只要问线路（丢包数据底层就有）；
- Q1 只要让更懂行的人（客户端 App 自己，或入口端口）来标记。

两张写死的表，就都没有存在的必要了。

## 5. 最终方案 D（详细展开）

### 5.1 Q2 —— 要不要双发？看线路丢包（删掉 `MEDIA_KEYS[]`）
把 middle 现在的判断（代码 `:524`）：
```
是直播优先级  且  域名像媒体(hit_media)   →  双发
```
改成：
```
是直播优先级  且  ( 线路丢包率 > L  或  抖动 > V )   →  双发
```
- **改动极小**：双发这个动作**本来就发生在 middle**（决定权、配对 ID 都在 middle，代码 `:524`/`:525`），所以只改这一行判断条件，再补上"丢包率怎么算"（见第 6 节），几十行代码。
- **线路好就不双发**（省下宝贵的跨国带宽），**线路差就自动开双发**（保护直播）。开销只在真正需要时才付出。
- **顺带解决一个协议难题**：因为"要不要双发"由 middle 用本地线路数据**自己决定**，不需要 entry 额外传一个"这是媒体"的标志过来（否则要改数据头部格式）。信令类小流量在丢包时也会被一起保护——这其实**更好**，因为信令丢包同样会拖慢直播打开，而它流量小、双发代价低。

### 5.2 Q1 —— 给不给快车道？让懂行的来标记（弱化/删掉 `pat[]`）
"这条流急不急"，最清楚的其实不是我们中转，而是**抖音客户端自己**。三个档次，从好到简单：

- **Q1-a 最理想（配合自研客户端，见 [06](06-custom-client.md)）**：我们自己的客户端在建连时，直接带一个"我是直播/延迟敏感"的标志。entry 一收到就知道，**零猜测**。
- **Q1-b 现实可行（继续用现成的 Shadowrocket 等客户端）**：entry **开两个入口端口**，让客户端的分流规则把"抖音直播"指向 A 端口、其它指向 B 端口。entry **按进来的是哪个端口**决定快慢车道。这样"哪些算直播"的名单**交给客户端的规则去维护**（这类工具本来就有可订阅、社区维护的抖音规则），不再写死在我们程序里。
- **Q1-c 兜底（单用户自己看）**：干脆**默认所有流量都上快车道**（保证直播开头不漏保护），然后在后台观察，把那些"持续大流量、明显是下载"的流**降级**踢出快车道（降级慢一点没关系，反正下载不急）。

### 5.3 关键：Q2 给 Q1 兜底，所以 Q1 不用很准
这是方案 D 优雅的地方：**因为 Q2（双发）已经改成看线路丢包了，Q1（快车道）判得糙一点也没关系**——
- 快车道里就算混进几条非直播流量，只要线路不丢包，它们也不会触发双发、不会浪费带宽；
- 于是 Q1 的精度要求大大降低，不必追求"精准识别抖音直播"。

## 6. 这方案能落地吗？—— 底层 picoquic 已验证支持

方案 D 全押在一件事上：**能不能拿到每条连接真实的丢包率？** 我们查了底层 picoquic 库的源码，答案是**能，而且现成**。

### 6.1 丢包数据在哪
picoquic 提供的"线路质量"结构体 `picoquic_path_quality_t`（代码 `picoquic.h:1198`）里已经有：

| 字段 | 含义 |
|---|---|
| `sent` | 这条连接一共发了多少个包 |
| `lost` | 其中被判定丢失的包数 |
| `spurious_losses` | "误判丢失"（以为丢了、其实后来到了）的包数——算丢包率时要**减掉**它 |
| `rtt` / `rtt_variant` / `rtt_max` | 延迟及**抖动**，可用于第 5.1 里的 `V`（抖动阈值） |

> **当前的坑**：代码 `nb_node.c:439` 现在把丢包率写死成了 `0.0`（占位符，从没真正算过）。所以之前"按丢包选路"其实一直在拿 0。**方案 D 的第一步就是把这里改成用上面这些真实字段。**

### 6.2 丢包率怎么算
**推荐用"增量"算法**（反映当前状态，而不是从头到现在的平均）：
```
记住上次的 sent、lost；这次再取一遍：
  这段时间发了     Δsent = 本次sent  - 上次sent
  这段时间丢了     Δlost = 本次lost  - 上次lost
  丢包率 loss% = 100 × Δlost / Δsent      （Δlost 里可再减去误判 spurious）
```
用累计值（总 lost / 总 sent）会被历史稀释，反应迟钝，不推荐。

### 6.3 更好的方式：不用轮询，让库主动通知
picoquic 还支持**订阅线路质量变化**：
- 调 `picoquic_subscribe_to_quality_update()`（代码 `picoquic.h:1224`）设定阈值；
- 线路变差越过阈值时，picoquic 主动触发回调 `picoquic_callback_path_quality_changed`（代码 `picoquic.h:417`）。

这样 middle **不用定时去查**，线路一变差就被通知、立刻开双发，线路恢复就关。更实时、更省 CPU。

### 6.4 三个技术校正（给实现者）
1. **用对 API**：我们的 6 条是各自独立的单路径连接，应该用 `picoquic_get_default_path_quality()`（代码 `picoquic.h:1221`，单路径专用），比现在代码 `:438` 用的那个带 path-id 的版本更直接准确。
2. **别用 QUIC 原生多路径替换我们的双发**：QUIC 的 multipath 是把流量**拆开分散**到多条路（为了提总带宽），而我们要的是**复制冗余**（为了抗丢包），**方向正好相反**。现有 `flowid` 双发+去重语义是对的，别动。
3. **阈值要实测标定**：`L`（丢包%）、`V`（抖动）、采样窗口、以及"滞回"（防止在阈值附近反复开关双发）——用 roadmap 里计划的 `tc netem`（人工注入丢包的工具）一起测出来。

## 7. 我们否决了哪些方案（记录原因，防止以后重走弯路）

| 方案 | 否决原因 |
|---|---|
| **纯行为在线学习**（观察流量大了再判定是直播） | 要先"看一段"才判定，**直播开头那几秒正好没保护**，违背低延迟目的 |
| **本地自学习补域名名单** | 抖音域名一直变，本地怎么学都**滞后**，追不上 |
| **只把写死表挪到配置文件热重载** | 解决了"要重编译"，但**没解决"域名多变追不上"** |
| **信令锚定 + 因果关联**（认几个稳定的信令域名，把它后面紧跟的新域名当直播） | 抖音 App 一打开**同时并发几十条连接**（信令/图片/推荐/埋点混杂），会**误把图片、埋点 CDN 当成直播**；且运营商 NAT 下多个用户共享一个 IP，无法区分是谁的流。误判风险太大 |
| **在 middle 维护域名表/做识别** | middle 是**无状态**中转，多用户流量混在一起，拿不到原始客户端信息，做不了也不该做 |

> 这些不是"错的想法"，而是**在"低延迟 + 域名多变"双重约束下走不通**。方案 D 通过"拆成 Q1/Q2"绕开了它们全部的坑。

## 8. 落地步骤与待确认

### 落地顺序（建议）
1. **补丢包采集**：修 `nb_node.c:439`，用 `get_default_path_quality` 取 `sent/lost/spurious_losses`，按 6.2 增量算 `loss%`（可选：接 6.3 的订阅回调）。
2. **改双发判据**：把 `:524` 的 `hit_media` 换成"丢包率/抖动超阈值"，**删掉 `MEDIA_KEYS[]`**。
3. **Q1 先用兜底档（5.2 Q1-c）**验证，随后视情况上 Q1-a（自研客户端标志）或 Q1-b（双入口端口）。
4. **标定阈值**：用 `tc netem` 注丢包，量化直播卡顿改善、定 `L/V/窗口/滞回`（并进 roadmap P0 的 FEC 量化计划）。

### 仍需实测确认的前提
1. **抖音媒体是否真的走进了我们隧道？**（如果它走 UDP/QUIC 直连、绕过代理，那隧道里根本没有直播大流量，一切优化落空）
   - 目前的**间接证据是乐观的**：entry 的 SOCKS5 只收 TCP、明确拒绝 UDP（代码 `:830`），而 roadmap 记录"手机实测直播正常"——两者同时成立，说明**抖音直播确实以 TCP 形态进了隧道**。但仍建议正式抓包确认。
2. **多用户场景**：若多个用户共用 entry，快车道（3 条）可能被挤爆，Q1 需要能把批量流分出去（Q1-a/b）。单用户自用则 Q1-c 足够。
