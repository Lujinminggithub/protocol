## 1. 排序原则

V1.5 的需求排序遵循 4 条原则：

1. **先保主链路稳定**：先做会直接影响现有三跳可用性和回归风险的部分。
2. **先做底座再做增强**：先做发送模型、扩容骨架、可观测性，再做 FEC。
3. **先做可代码级验证的项**：优先做能在本地/实验环境复现和验收的内容，把“手机直播真机测试”放到最后。
4. **先做依赖少的项**：避免后面的特性建立在不稳定或未重构的代码上。

## 2. 总体节奏

V1.5 的实施节奏固定为：

1. 排序并冻结需求
2. 逐项实现
3. 每项完成后先做代码级测试
4. 所有代码项完成后再做三跳联调
5. 最后做直播测试

也就是说：

- **过程中允许做本地、单机、三跳、netem、压测等代码级测试**
- **不在中途反复做手机直播联调**
- **手机直播测试作为最终整体验收**

## 3. 优先级总表

### P0 — 必须先完成

1. **发送模型改造：`add_to_stream` → `prepare_to_send`**
2. **FEC 基础骨架：datagram 能力接入 + 控制流协议骨架**
3. **单向纠错闭环：`middle -> exit`**
4. **可靠补发回退：`NACK / RETX`**
5. **反向纠错闭环：`exit -> middle`**
6. **FEC 观测与 netem 量化**

### P1 — 在 P0 后完成

1. **多 worker + `SO_REUSEPORT` 扩容骨架**
2. **链路质量驱动的 FEC 自适应开关**
3. **控制面底座：路由/出口选择接口**
4. **认证与 QoS 的服务端接口预留**

### P2 — V1.5 完成前的收尾

1. **运维命令和日志更新**
2. **文档与回归脚本补齐**
3. **三跳全链路回归**
4. **最终直播测试**

## 4. 逐项说明

### 4.1 P0-1 发送模型改造

目标：

- 把当前主数据发送路径从 `picoquic_add_to_stream()` 迁到 `picoquic_callback_prepare_to_send`
- 为后续 FEC 和多 worker 降低复制与排队成本

为什么排第一：

- 这是整个 V1.5 数据面的底座
- 后面的 FEC sidecar 和 datagram 发送都更适合建立在 JIT 发送模型上
- 如果不先改，后续 FEC 统计和性能判断会被旧发送模型污染

验收标准：

- 普通三跳可靠流功能不退化
- 大文件、并发流、SOCKS 模式都能正常工作
- 现有关键回归项通过

测试方式：

- 单机 loopback
- 三跳 curl / md5 / 并发压测
- 与旧版对比 CPU、RSS、吞吐、首包时延

### 4.2 P0-2 FEC 基础骨架

目标：

- 接入 QUIC datagram 能力
- 打通 FEC 控制流
- 实现 `START / BLOCK_META / FIN / RST`

为什么排第二：

- 没有这个骨架，就没有后续纠错能力
- 这是“去掉双发”的第一步

验收标准：

- `middle <-> exit` 可建立 FEC hop session
- datagram 能收能发
- 控制流消息解析稳定

测试方式：

- 本地单元测试
- middle/exit 双节点回环测试
- 日志级验证消息时序

### 4.3 P0-3 单向纠错闭环

目标：

- 先实现 `middle -> exit` 单向 source + repair + decode

为什么排第三：

- 正向方向是当前最核心的直播路径
- 先做单向比双向更易控风险

验收标准：

- 在人工丢包下可恢复缺失 source symbol
- 能正确顺序交付到 exit 的下游 TCP

测试方式：

- `tc netem` 注入随机丢包
- block 级恢复统计
- 单流与少量并发测试

### 4.4 P0-4 可靠补发回退

目标：

- 为不可恢复 block 增加 `NACK / RETX`
- 保证最终 TCP 语义不丢字节

为什么排第四：

- 没有它，FEC 只能做“尽力而为”
- V1.5 仍是 `TCP-over-QUIC`，最终可靠性不能丢

验收标准：

- FEC 恢复失败时能正确补齐
- 不出现永久洞或错误 FIN

测试方式：

- 高丢包 / 突发丢包
- 人工制造“超过 r 个丢失”的 block
- 观察 NACK/RETX 时序

### 4.5 P0-5 反向纠错闭环

目标：

- 对称支持 `exit -> middle`

为什么排第五：

- 回程同样影响直播体验
- 但先做正向更容易定位问题

验收标准：

- 回程 block 能编码、恢复、补发
- 最终 entry 收到的 TCP 字节完整

测试方式：

- 下载型回程流
- 模拟直播下行数据
- 双向同时压测

### 4.6 P0-6 FEC 观测与量化

目标：

- 把“能跑”变成“可量化”

关键指标：

- `fec_block_started`
- `fec_block_decoded`
- `fec_block_decode_fail`
- `fec_nack_sent`
- `fec_retx_sent`
- `fec_recovered_bytes`
- `fec_extra_bytes`
- `fec_overhead_pct`
- `fec_block_latency_us`

为什么排第六：

- 在逻辑闭环完成后做统计才有意义

验收标准：

- 能稳定输出指标
- 能支撑参数调优

测试方式：

- `tc netem`
- 压测脚本
- 多组 `k/r` 对比

## 5. 第二优先级

### 5.1 P1-1 多 worker + `SO_REUSEPORT`

目标：

- 把单线程从“唯一实例”升级为“单 worker 模型”
- 节点层面吃到多核

依赖：

- P0 数据面先稳定

验收标准：

- 多 worker 独立 `quic context`
- 新连接可分流
- 单 worker 故障不拖垮全局

### 5.2 P1-2 FEC 自适应开关

目标：

- 让 FEC 不再硬编码开关

依赖：

- P0 指标齐全

验收标准：

- 能按 `loss / jitter / cold start` 自动启停
- 有回滞

### 5.3 P1-3 控制面底座

目标：

- 先把服务端的选路和出口编排接口搭起来

依赖：

- 数据面与 FEC 稳定

### 5.4 P1-4 认证与 QoS 接口预留

目标：

- 不要求本阶段闭环上线
- 但要留出协议和代码边界

## 6. 最终验收顺序

### 6.1 代码级验收

按这个顺序：

1. 单元级/结构级测试
2. 单机 loopback 测试
3. 双节点 FEC hop 测试
4. 三跳联调
5. `tc netem` 丢包/抖动测试
6. 并发与吞吐测试

### 6.2 最终业务验收

仅在所有代码项完成后再做：

1. 手机普通视频测试
2. 手机直播测试
3. 长时稳定性测试

## 7. 建议的实现节奏

接下来建议严格按以下顺序推进：

1. `prepare_to_send` 改造
2. datagram/FEC 控制流骨架
3. 单向正向纠错
4. `NACK / RETX`
5. 反向纠错
6. FEC 指标与 netem
7. 多 worker
8. FEC 自适应
9. 控制面底座
10. 最终三跳与直播测试

## 8. 一句话结论

V1.5 的需求排序应该是：

**先做发送底座，再做纠错闭环，再做扩容与控制面，最后再做直播测试。**
