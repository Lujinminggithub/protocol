# NB V1.5 纠错型 FEC 详细设计稿

> [01-需求](01-requirements.md) | [02-架构](02-architecture.md) | [03-已实现](03-implementation.md) | [04-部署运维](04-deployment-ops.md) | [05-路线图](05-roadmap.md) | [08-V1.5实施方案](08-V1.5实施方案.md) | 09-V1.5纠错型FEC详细设计稿(本篇)

## 1. 设计结论

V1.5 的 FEC 采用：

**坏跳内部混合式 FEC**

- 原始业务形态继续保持 `TCP-over-QUIC`
- 只在受保护坏跳上启用
- 去掉当前“双发两条可靠 stream”的方案
- 改为“原始分片 + 修复分片”的纠错型 FEC
- 为了不打破端到端 TCP 语义，引入可靠补发回退

一句话解释：

> 在 `middle -> exit` 这条坏跳上，业务字节不再通过“复制整条 stream”抗抖动，而是被切成分片，使用 `源分片 + 修复分片` 发送；若仍无法恢复，再用稀疏的可靠补发兜底，确保 TCP 语义最终不丢字节。

## 2. 设计目标

### 2.1 要解决的问题

当前双发方案的问题：

1. 2 倍带宽放大
2. 2 倍发送排队与复制
3. 2 倍 ACK / 恢复 / 日志压力
4. 在长期差线场景下，可能反过来加重瓶颈

V1.5 新 FEC 的目标：

1. 在 `hk -> kz` 坏跳上降低直播毛刺
2. 额外带宽显著低于双发
3. 不要求客户端配合
4. 不改变当前 `TCP-over-QUIC` 产品对外语义
5. 允许将来平滑演进到 V2 的 datagram/chunk 体系

### 2.2 不做的事情

本稿明确不做：

- 自研手机客户端
- 全量 datagram 实时平面
- 客户端侧 FEC
- 客户端侧 multipath
- 摆脱 TCP-over-QUIC 的整体产品形态

## 3. 适用范围

### 3.1 保护方向

V1.5 第一阶段只保护：

- `middle -> exit`
- `exit -> middle`

也就是当前已知最差的跨境 hop。

### 3.2 保护流量

仅对以下流开启：

- `prio == PRIO_LATENCY`
- 被控制面或本地规则标记为直播敏感流

不对以下流开启：

- 普通网页
- 批量下载
- 非直播 API

### 3.3 作用层级

这是按跳内部增强，不是端到端新协议：

- `entry -> middle` 仍按当前 stream relay
- `middle <-> exit` 在受保护方向启用 FEC hop protocol
- `exit -> target TCP` 仍是普通 TCP

## 4. 核心方案

### 4.1 为什么不能继续在可靠 stream 上做纠错

如果仍把原始数据和修复数据都放进可靠 QUIC stream：

1. 修复数据也会被 QUIC 自己可靠重传
2. 原始业务字节仍受 stream HOL 限制
3. 修复与业务数据之间无法真正解耦

所以 V1.5 的纠错必须把“坏跳内部的数据承载方式”从纯 stream relay 升级为：

- 可靠控制流
- 不可靠原始/修复分片通道
- 可靠补发兜底

### 4.2 推荐承载方式

在受保护 hop 内部，采用三种载体：

1. **FEC 控制流**
   - QUIC bidi stream
   - 可靠
   - 负责 `START / BLOCK_META / NACK / RETX / FIN / RST`
2. **源分片数据报**
   - QUIC datagram
   - 不可靠
   - 承载原始切片
3. **修复分片数据报**
   - QUIC datagram
   - 不可靠
   - 承载 parity / repair symbol
4. **可靠补发**
   - 复用 FEC 控制流
   - 仅在纠错失败时按需发送缺失分片

这不是引入完整的 V2 实时平面，而是在单个坏跳内部使用 datagram 作为 FEC sidecar。

## 5. 受保护坏跳协议

### 5.1 会话建立

当 `middle` 判断某条流需要坏跳 FEC 时：

1. 不再为该流向 `exit` 打开普通业务下游 payload stream
2. 改为打开一条 FEC 控制流
3. 在控制流首部发送：
   - `版本`
   - `session_id`
   - `方向能力`
   - `prio`
   - `目标地址/端口`
   - `FEC 参数`
   - `模式 = fec-hop-v1`

`exit` 收到后：

1. 创建 target TCP
2. 初始化该 `session_id` 的 FEC 收发状态
3. 后续业务 payload 默认走 datagram 分片，不再依赖该控制流承载主数据

### 5.2 会话对象

每条受保护逻辑流维护一个 `fec_hop_session`：

- `session_id`
- `ctrl_cnx`
- `ctrl_stream_id`
- `prio`
- `flow_direction_mask`
- `tx_forward`
- `rx_forward`
- `tx_reverse`
- `rx_reverse`
- `target metadata`
- `reorder / deliver state`

## 6. FEC 数据模型

### 6.1 基本概念

#### 字节流

原始业务仍是有序字节流。

#### 分片

把字节流切成固定大小的 `symbol`：

- `symbol_payload = 960 bytes`

选择 960 的原因：

- 便于在单个 QUIC datagram 中稳定承载
- 为 QUIC header、datagram frame header、自定义 FEC header 留足空间

#### 保护块

每 `k` 个源分片组成一个 block：

- 默认 `k = 8`
- 默认 `r = 2`
- 即每 8 个源分片生成 2 个修复分片
- 默认额外带宽约 25%

单 block 原始净载荷：

- `8 * 960 = 7680 bytes`

### 6.2 参数建议

首版默认参数：

- `symbol_payload = 960`
- `k = 8`
- `r = 2`
- `block_max_hold_us = 2000`
- `nack_wait_us = 3000`
- `max_retx_per_block = 1`

自适应参数建议：

- 轻微波动：`k=8 r=1`
- 常态坏线：`k=8 r=2`
- 高丢包坏线：`k=6 r=2`

## 7. 编码算法选择

### 7.1 推荐

V1.5 推荐使用：

- **系统码 Reed-Solomon over GF(2^8)**

原因：

1. 能恢复多于 1 个丢失分片
2. 与 `k/r` 参数化天然匹配
3. 适合按 block 编码
4. 语义清晰，便于统计恢复率

### 7.2 不推荐

不建议把 V1.5 首版做成：

- 仅 1 个 XOR parity
- 仅复制部分分片

因为这两种都太弱，无法覆盖 `hk -> kz` 这种明显波动链路。

### 7.3 实现建议

首版建议：

- vendored 一个轻量 GF(256) RS 实现
- 保持依赖最少
- 只支持小 `k/r` 组合

## 8. 线协议设计

### 8.1 控制流消息

控制流使用 TLV 或定长头 + 变长载荷，消息类型建议如下：

#### `START`

建立会话：

- `session_id`
- `prio`
- `target_host`
- `target_port`
- `fec_profile_id`
- `k`
- `r`
- `symbol_payload`

#### `BLOCK_META`

声明一个 block 已封口：

- `session_id`
- `direction`
- `block_id`
- `src_count`
- `repair_count`
- `raw_bytes`
- `sealed_at_us`

#### `NACK`

接收端发起补发：

- `session_id`
- `direction`
- `block_id`
- `missing_bitmap`

#### `RETX`

发送端在可靠控制流中补发缺失分片：

- `session_id`
- `direction`
- `block_id`
- `symbol_index`
- `payload_length`
- `payload`

#### `FIN`

- `session_id`
- `direction`
- `final_block_id`

#### `RST`

- `session_id`
- `error_code`

### 8.2 Datagram 头

建议每个 FEC datagram 带固定头：

- `version`
- `session_id`
- `direction`
- `block_id`
- `symbol_index`
- `symbol_type`
  - `0 = source`
  - `1 = repair`
- `payload_length`
- `flags`

## 9. 发送端状态机

### 9.1 正向方向（middle -> exit）

发送逻辑：

1. 从上游 QUIC stream 收到业务字节
2. 追加到 `tx_forward` 字节缓存
3. 累积到 `symbol_payload` 就切成 1 个 source symbol
4. source symbol 立即排入 datagram 发送队列
5. 当出现以下任一条件，封口当前 block：
   - `src_count == k`
   - `block_max_hold_us` 到时
   - 收到上游 FIN
6. block 封口后立即生成 `r` 个 repair symbol
7. 发送 `BLOCK_META`
8. 将 repair symbol 排入 datagram 发送队列

### 9.2 反向方向（exit -> middle）

对称处理：

1. 从 target TCP 收到业务字节
2. 追加到 `tx_reverse`
3. 同样切片、封块、编码、发送

## 10. 接收端状态机

### 10.1 block 缓存

每个方向维护一个 `rx_block_map`：

- `block_id -> block_state`

每个 `block_state` 包含：

- `src_count_expected`
- `repair_count_expected`
- `raw_bytes`
- `source_received_bitmap`
- `repair_received_bitmap`
- `source_symbols[]`
- `repair_symbols[]`
- `sealed`
- `decoded`
- `nack_sent`

### 10.2 接收流程

1. 收到 source datagram：放入对应 block
2. 收到 repair datagram：放入对应 block
3. 收到 `BLOCK_META`：标记 block 已封口
4. 每次有新 symbol 或 block meta 到达时尝试恢复：
   - 若 source 已齐，直接通过
   - 若 `source + repair >= src_count_expected`，尝试 RS 解码
5. 解码成功后生成完整原始分片序列
6. 若 block 已封口，且等待 `nack_wait_us` 后仍不可解，则发送 `NACK`

## 11. 顺序交付与最终可靠性

### 11.1 顺序交付

因为最终仍要回到 TCP 语义，所以必须按序交付。

每个方向维护：

- `next_deliver_block_id`

交付规则：

- 只有当 `next_deliver_block_id` 已 `decoded` 时，才可向下游交付
- 交付后递增，尝试连续释放后续 block

### 11.2 最终可靠性

如果 block 无法仅靠 FEC 恢复：

1. 接收端发送 `NACK`
2. 发送端在可靠控制流上回送 `RETX`
3. 接收端补齐缺失 symbol
4. block 完整后继续顺序交付

这保证了：

- 正常情况依靠 FEC 低延迟恢复
- 极端情况仍能靠可靠补发保住 TCP 语义

## 12. FIN / RESET / 超时

### 12.1 FIN

发送端收到业务 FIN 后：

1. 封口最后一个 block
2. 发送最后 repair
3. 发送 `FIN`

接收端只有在所有小于等于 `final_block_id` 的 block 都已交付后才向下游发 FIN。

### 12.2 RESET

任何一侧异常：

1. 发送 `RST`
2. 清空 block 状态
3. 关闭 target TCP 或上游 stream

### 13.2 需要新增的结构

新增：

- `fec_hop_session_t`
- `fec_dir_tx_t`
- `fec_dir_rx_t`
- `fec_block_tx_t`
- `fec_block_rx_t`

- `fec_enabled`

### 13.3 需要新增的 picoquic 能力接入

现有代码要新增这些回调处理：

- `picoquic_callback_prepare_datagram`
- `picoquic_callback_datagram`
- `picoquic_callback_datagram_lost`
- `picoquic_callback_datagram_acked`
- `picoquic_callback_datagram_spurious`

同时需要在 QUIC transport parameter 上开启 datagram 支持。

### 13.4 与 `prepare_to_send` 的关系

V1.5 推荐把两件事一起做：

1. 可靠 stream 主发送路径改成 `prepare_to_send`
2. FEC sidecar datagram 使用 `prepare_datagram`

这样：

- stream 不再大量 `add_to_stream`
- datagram 也不需要大队列复制
- 整个发送面都更接近 picoquic 推荐模式

## 15. 实施顺序

### 第一步：协议骨架

- 定义控制流消息
- 定义 datagram 头
- 打通 `START / BLOCK_META / FIN / RST`

### 第二步：单向正向纠错

- 先只做 `middle -> exit`
- 先不做反向
- 先打通 source + repair + decode

### 第三步：可靠补发

- 增加 `NACK / RETX`
- 保证最终可靠性

### 第四步：反向方向

- 再对称支持 `exit -> middle`

### 第五步：自适应与量化

- 接入 linkq 开关
- 完成 netem 压测

## 16. 一句话总结

V1.5 的纠错型 FEC 推荐方案是：

**在 `middle <-> exit` 坏跳内部，用“可靠控制流 + datagram 源分片/修复分片 + 稀疏可靠补发”替换当前“双发可靠 stream + 去重”方案。**

它既去掉了双发，又保留了当前 `TCP-over-QUIC` 主线，并为 V2 的 datagram/chunk 实时平面提前铺好了实现路径。
