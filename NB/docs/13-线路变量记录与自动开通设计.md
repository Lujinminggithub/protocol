# NB 线路变量记录与自动开通设计

## 1. 文档目的

本文记录上海线路与广州-香港-KZ 线路在阶段性测试中的拓扑、最终生效变量、历史试验变量和代码级修正，并定义产品化后的线路探测、参数生成、灰度开通与回滚流程。

记录原则：

- “当前基线”只记录已经部署且通过代码测试的配置。
- CUBIC、fastcc、关闭 GSO、主动 FEC 等仅作为历史试验，不得自动继承到生产线路。
- `linkq loss` 必须扣除已确认的 spurious loss，不能直接等同于物理链路丢包。
- 空闲探测不能代替带负载探测；重排序和 ACK 压缩通常只在接近直播码率时出现。

## 2. 两条线路对比

| 项目 | 上海线路阶段基线 | 广州-香港-KZ 当前基线 |
|---|---|---|
| 拓扑 | 上海 `115.175.66.203` -> US relay `154.7.182.135` -> US exit `207.168.53.38` | 广州 `106.75.169.83` -> 香港内网 `172.16.31.28` -> KZ `2.135.147.106` |
| 客户端入口 | `115.175.66.203:1080` | `106.75.169.83:1080` |
| entry -> middle RTT | 约 `150-190ms` | 约 `4.3-4.7ms` |
| middle -> exit RTT | 约 `1-5ms` | 约 `189-231ms` |
| 主要异常 | entry -> middle 长 RTT、ACK 停顿、BBR 下限连续衰减 | middle -> exit 最大约 `66包/296ms` 重排序，大量伪丢包 |
| 数据面地址 | 公网地址 | 广州 -> 香港强制使用内网专线地址 `172.16.31.28` |
| 连接池 | `POOL_SIZE=1` | `POOL_SIZE=1` |
| worker | entry `1` / middle `1` / exit `2` | entry `1` / middle `1` / exit `2` |
| FEC | `observe=1, active=0` | `observe=1, active=0` |

## 3. 当前生效变量

### 3.1 通用变量

| 变量 | 当前值 | 作用 | 变更方式 |
|---|---:|---|---|
| `NB_CC` | 按每跳 profile | 当前广州专线 entry 为 `cubic`，middle/exit 为 `bbr` | 重连生效 |
| `NB_BBR_OPTIONS` | middle 为 `Q0.0001:F0.25:`，exit 为 `Q0.0001:` | BBR pacing quantum 与长 RTT 快速恢复窗口下限 | 重连生效 |
| `NB_CWIN_MAX_BYTES` | entry 为 `524288`，其余未设置 | 限制低 RTT 专线 CUBIC 窗口异常膨胀 | 重连生效 |
| `NB_SOCKS_UDP_ADVERTISE_IP` | `106.75.169.83` | SOCKS5 UDP_ASSOCIATE 对手机返回的可达公网地址 | 进程重启 |
| `NB_SOCKS_UDP_PORT_MIN/MAX` | `20000/21023` | 200 条线路使用的 1024 端口固定 UDP relay 池 | 进程重启 |
| `NB_UDP_GSO` | `on` | UDP GSO 聚合 | 进程重启 |
| `NB_FEC_V15` | `on` | 仅开启 FEC 观察和门控日志 | 进程重启 |
| `NB_FEC_V15_ACTIVE` | 未设置 | 不接管业务数据 | 受控测试才可开启 |
| `POOL_SIZE` | `1` | 每个下一跳仅一个 QUIC 拥塞控制实例 | 当前为编译期常量 |
| route bootstrap priority | `0` | latency 流 route header 临时最高优先级 | 编译期行为 |

说明：日志中的 `NB_FEC_V15=on` 不代表 FEC 数据面已启用，必须同时看到 `active=1` 才表示 source/repair 接管业务流。

### 3.2 上海线路阶段参数

| 位置 | 参数 | 值 | 来源 |
|---|---|---:|---|
| entry -> middle | `NB_REORDER_GAP` | `20` | 针对约 `13-16包` 重排序留余量 |
| entry -> middle | `NB_REORDER_DELAY_US` | `30000` | 早期保守值，未覆盖后续观测到的秒级 ACK 停顿 |
| middle -> exit | reorder gap/delay | picoquic 默认 `3/0ms` | 该段低 RTT，阶段测试未单独校准 |

该线路后续不作为默认部署线路，配置保留仅用于对照和回归。

### 3.3 广州-香港-KZ 当前参数

| 位置 | 参数 | 值 | 实测依据 |
|---|---|---:|---|
| entry -> middle | 下一跳地址 | `172.16.31.28:4443` | 广州到香港内网专线 |
| entry -> middle | `NB_REORDER_GAP` | `20` | 专线保守容忍值 |
| entry -> middle | `NB_REORDER_DELAY_US` | `30000` | PTO 不变，仅延后早期 loss 判定 |
| entry -> middle | `NB_CC` | `cubic` | 低 RTT 专线突发时避免 BBR 小 BDP/cwin 塌缩 |
| entry -> middle | `NB_CWIN_MAX_BYTES` | `524288` | 将 CUBIC 最大拥塞窗口限制为 `512KiB`，避免 app-limited 后窗口膨胀到数十至数百 MB |
| middle -> exit | 下一跳地址 | `2.135.147.106:4443` | 新 KZ 出口 |
| middle -> exit | `NB_CC` | `bbr` | 长 RTT 公网链路继续使用带宽模型 |
| middle -> exit | `NB_BBR_OPTIONS` | `Q0.0001:F0.25:` | 快速恢复时窗口不低于恢复前窗口的 `25%`，避免瞬间降到 `3KB`；仅影响 middle 新连接 |
| middle -> exit | `NB_REORDER_GAP` | `80` | 实测最大重排序 gap 约 `66` |
| middle -> exit | `NB_REORDER_DELAY_US` | `350000` | 实测最大重排序延迟约 `296ms` |

调整前 middle -> KZ 每 10 秒会产生约 `200-500` 次重传判断，其中约 `70%-85%` 最终被确认是伪丢包，BBR 带宽估计从约 `22Mbps` 降到 `3.5-6.6Mbps`。调整后真实连接日志必须显示：

```text
tol=80/350.0ms
```

仅看到 systemd 环境变量不算生效，必须检查新建 picoquic 连接的 `linkq` 日志。

## 4. 已落地的 picoquic 与发送路径修正

1. ACK-only 包在连续 timer retransmit 条件下不再计入有效 loss，也不向拥塞控制重复发送错误信号。
2. BBR 长 RTT 路径的 `bw_lo/inflight_lo` 不再在同一 ProbeBW 周期内按 beta 每个 RTT 连续复合衰减。
3. app-limited startup 退出时保留近期有效带宽下限。
4. entry 和 middle 的下游 client 连接都支持调用 `picoquic_set_loss_reorder_tolerance()`。
5. latency 流的 route header 临时使用最高优先级，首部交给 QUIC 后立即恢复策略优先级。
6. FEC 保持观察模式，当前稳定基线不启用 source/repair 数据面。
7. entry 使用 picoquic 原生 `cwin_max` 将 CUBIC 窗口限制为 `512KiB`。
8. BBR 新增可选 `F` 参数；长 RTT 快速恢复时可按恢复前窗口比例设置下限，本线路仅 middle 使用 `F0.25`，exit 保持原行为。

## 5. 历史单变量试验结论

| 试验 | 结果 | 产品化结论 |
|---|---|---|
| `NB_CC=cubic` | 部分窗口相对稳定，但仍出现红黄切换 | 保留为回退算法，不作为当前默认 |
| `NB_CC=fastcc` | 开播红色持续较久 | 不自动选择 |
| BBR + `Q0.0001:` | 配合 ACK/loss 修正后整体最好 | 当前默认 |
| 关闭 NB 自定义 UDP GSO | 出现直接连接中断 | 当前保持开启 |
| 多连接池 | 多连接竞争使直播表现劣于纯 HY2 的可能性较高 | 当前固定单连接基线 |
| entry/middle 多 worker | middle 的共享 UDP 回包无法跨 picoquic context 分派 | middle 当前强制单 worker |
| 主动纠错 FEC | 早期版本出现延迟、卡顿和进程风险 | 完成模块化和矩阵验证前仅观察 |

## 6. 产品化自动开通是否可行

可以，但不能只执行 `ping` 或空闲 QUIC 握手后直接开通。推荐使用“静态检查 + 带负载预检 + 参数生成 + 小流量灰度 + 持续校准”五阶段流程。

### 6.1 阶段一：静态检查

- 校验证书、节点身份、系统时间和目标二进制哈希。
- 检查 UDP 端口、防火墙、MTU、socket buffer、CPU 和文件描述符上限。
- 确认数据面地址；存在 `private_ip` 时优先使用内网地址。
- 检查出口公网 IP 和 TikTok 白名单是否符合线路配置。

### 6.2 阶段二：带负载 QUIC 预检

每一跳独立运行至少 `90-180s`，流量模型应达到目标直播峰值的 `1.25倍`，并同时包含小控制流和持续媒体流。采集：

- RTT 的 min、P50、P95、P99 和 max。
- RTT variation 与 ACK delay。
- raw loss、effective loss、spurious loss 和 timer loss。
- reordering gap 和 reordering delay 的 P99/P99.9/max。
- delivery rate、pacing rate、cwin、bytes in flight 和 blocked 状态。
- CPU、事件循环延迟、socket drop 和发送队列水位。

探测样本不足 `10000` 个数据包时，不允许自动生成生产参数。

### 6.3 阶段三：生成线路参数

建议算法：

```text
reorder_gap = 向上取整(P99.9重排序包数 * 1.20)，限制在 3..256
reorder_delay = P99.9重排序延迟 + max(10ms, 0.25 * min_rtt)
reorder_delay 上限 = min(1000ms, 2 * 稳态RTT)
```

当前 KZ 样本 `66包/296ms` 按该规则约为 `80包/343ms`，工程取整为 `80包/350ms`。

其他决策：

- `effective_loss` 必须使用 `raw_loss - spurious_loss`，并过滤小样本窗口。
- FEC 只能在有效随机丢包持续超阈值且带宽余量足够时进入候选，不能因 raw loss 高直接开启。
- CC 不建议每条线路自动频繁切换；默认 BBR，CUBIC 仅作为经过同一矩阵验证的回退配置。
- worker 数由 CPU、包率和角色能力决定，不应由 RTT/loss 自动推导。
- 连接池大小属于架构容量参数，不应在单次线路探测后自动扩大。

### 6.4 阶段四：灰度开通

- 先用一个测试账号或 `1%-5%` 流量运行 `10-15分钟`。
- 检查首字节 P95、持续码率、spurious ratio、直播状态和观看端延迟。
- 灰度失败立即回退上一份已签名线路配置，不现场连续试多个变量。
- 灰度通过后再提升到全量。

### 6.5 阶段五：运行期校准

运行期可以自动调整 reorder tolerance，但必须满足：

- 使用滑动窗口和迟滞，至少连续多个有效窗口才升档或降档。
- 升档速度可以快，降档必须慢，避免参数抖动。
- 每次只调整 gap 或 delay 中的一个变量并记录版本。
- 参数变化要求新建 QUIC 连接生效，旧连接不原地修改。
- 不自动开启主动 FEC；FEC 需要独立的 canary 和完整性指标。

## 7. 控制面需要补齐的能力

当前自动化前仍需完成：

1. 将 `NB_CC`、BBR options、reorder 参数、GSO、worker 和连接池从部署脚本/编译常量迁移到版本化线路配置。
2. 提供独立的每跳探针，不通过业务日志反推线路参数。
3. 建立线路配置签名、审批、灰度比例、回滚版本和审计记录。
4. 建立参数生效回读；控制面下发值必须与 `linkq tol/cc` 实际值一致。
5. 为真实丢包、伪丢包、重排序、队列等待和直播业务状态建立统一时间线。

建议配置模型：

```json
{
  "line": "gz-hk-kz",
  "version": 2,
  "entry_middle": {
    "host": "172.16.31.28",
    "reorder_gap": 20,
    "reorder_delay_us": 30000
  },
  "middle_exit": {
    "host": "2.135.147.106",
    "reorder_gap": 80,
    "reorder_delay_us": 350000
  },
  "transport": {
    "cc": {"entry": "cubic", "middle": "bbr", "exit": "bbr"},
    "cwin_max_bytes": {"entry": 524288},
    "bbr_options": {"middle": "Q0.0001:F0.25:", "exit": "Q0.0001:"},
    "udp_gso": true,
    "fec_mode": "observe",
    "pool_size": 1
  },
  "workers": {"entry": 1, "middle": 1, "exit": 2}
}
```

## 8. 当前结论

产品化时可以先自动测试线路，再生成参数并开通，但必须以带负载 QUIC 探测和灰度验证为前提。可以在开通前可靠确定的主要是地址、MTU、RTT、ACK、重排序容忍度和基础 socket 参数；CC、FEC、连接池与 worker 不能仅根据一次线路测试自动决定。
