# NB 线路变量记录与自动开通设计

## 1. 文档目的

本文记录上海线路与广州-香港-KZ 线路在阶段性测试中的拓扑、最终生效变量、历史试验变量和代码级修正，并定义产品化后的线路探测、参数生成、灰度开通与回滚流程。

记录原则：

- “当前基线”只记录已经部署且通过代码测试的配置。
- CUBIC、fastcc、关闭 GSO、主动 FEC 等仅作为历史试验，不得自动继承到生产线路。
- `linkq loss` 必须扣除已确认的 spurious loss，不能直接等同于物理链路丢包。
- 空闲探测不能代替带负载探测；重排序和 ACK 压缩通常只在接近直播码率时出现。

## 3. 当前生效变量

### 3.1 通用变量

| 变量 | 当前值 | 作用 | 变更方式 |
|---|---:|---|---|
| `NB_CC` | 按每跳 profile | 当前广州专线 entry 为 `cubic`，middle/exit 为 `bbr` | 重连生效 |
| `NB_BBR_OPTIONS` | middle 为 `Q0.0001:F0.25:`，exit 为 `Q0.0001:` | BBR pacing quantum 与长 RTT 快速恢复窗口下限 | 重连生效 |
| `NB_CWIN_MAX_BYTES` | entry 为 `524288`，其余未设置 | 限制低 RTT 专线 CUBIC 窗口异常膨胀 | 重连生效 |
| `NB_SOCKS_UDP_ADVERTISE_IP` | `106.75.169.83` | SOCKS5 UDP_ASSOCIATE 对手机返回的可达公网地址 | 进程重启 |
| `NB_SOCKS_UDP_PORT_MIN/MAX` | `20000/21023` | 200 条线路使用的 1024 端口固定 UDP relay 池 | 进程重启 |
| `NB_UDP_GSO` | `off` | 当前稳定基线逐个发送 picoquic 已 pacing 的包，避免 NB 自定义 GSO 聚合改变突发形态 | 进程重启 |
| `NB_UDP_CONTROL_GRACE_US` | `120000000` | 手机关闭 SOCKS UDP 控制 TCP 后保留关联 120 秒，避免直播 UDP 被立即回收 | 进程重启 |
| `NB_FEC_V15` | `on` | 仅开启 FEC 观察和门控日志 | 进程重启 |
| `NB_FEC_V15_ACTIVE` | 未设置 | 不接管业务数据 | 受控测试才可开启 |
| `POOL_SIZE` | `1` | 每个下一跳仅一个 QUIC 拥塞控制实例 | 当前为编译期常量 |
| route bootstrap priority | `0` | latency 流 route header 临时最高优先级 | 编译期行为 |
| ctrl 调度预算 | `1Mbps + 32KB burst` | 有媒体积压时限制严格优先级抢占；无媒体时工作保持 | 运行期 |
| ctrl 队列水位 | `64KB/32KB` | 控制流高/低水位 | 运行期 |
| media 队列水位 | `256KB/64KB` | 可靠媒体流高/低水位；UDP deadline 为 `200ms` | 运行期 |
| bulk 队列水位 | `1MB/512KB` | 批量流高/低水位 | 运行期 |

说明：日志中的 `NB_FEC_V15=on` 不代表 FEC 数据面已启用，必须同时看到 `active=1` 才表示 source/repair 接管业务流。

### 3.2 上海线路阶段参数

| 位置 | 参数 | 值 | 来源 |
|---|---|---:|---|
| entry -> middle | `NB_REORDER_GAP` | `20` | 针对约 `13-16包` 重排序留余量 |
| entry -> middle | `NB_REORDER_DELAY_US` | `30000` | 早期保守值，未覆盖后续观测到的秒级 ACK 停顿 |
| middle -> exit | reorder gap/delay | picoquic 默认 `3/0ms` | 该段低 RTT，阶段测试未单独校准 |

该线路后续不作为默认部署线路，配置保留仅用于对照和回归。

### 3.3 广州-香港-KZ 当前参数

| 位置 | 参数 | 值 | 实测依据 |
|---|---|---:|---|
| entry -> middle | 下一跳地址 | `172.16.31.28:4443` | 广州到香港内网专线 |
| entry -> middle | `NB_REORDER_GAP` | `128` | 当前单变量基线；运行期按 late ACK/spurious P95/P99 自适应 |
| entry -> middle | `NB_REORDER_DELAY_US` | `450000` | 当前单变量基线；PTO 不变，运行期只快升慢降 |
| entry -> middle | `NB_CC` | `cubic` | 低 RTT 专线突发时避免 BBR 小 BDP/cwin 塌缩 |
| entry -> middle | `NB_CWIN_MAX_BYTES` | `524288` | 将 CUBIC 最大拥塞窗口限制为 `512KiB`，避免 app-limited 后窗口膨胀到数十至数百 MB |
| middle -> exit | 下一跳地址 | `2.135.147.106:4443` | 新 KZ 出口 |
| middle -> exit | `NB_CC` | `bbr` | 长 RTT 公网链路继续使用带宽模型 |
| middle -> exit | `NB_BBR_OPTIONS` | `Q0.0001:F0.25:` | 快速恢复时窗口不低于恢复前窗口的 `25%`，避免瞬间降到 `3KB`；仅影响 middle 新连接 |
| middle -> exit | `NB_REORDER_GAP` | `128` | 覆盖历史最大约 `98包` 重排序，并作为自适应下限 |
| middle -> exit | `NB_REORDER_DELAY_US` | `450000` | 覆盖历史最大约 `345ms` 重排序，并作为自适应下限 |

调整前 middle -> KZ 每 10 秒会产生约 `200-500` 次重传判断，其中约 `70%-85%` 最终被确认是伪丢包，BBR 带宽估计从约 `22Mbps` 降到 `3.5-6.6Mbps`。调整后真实连接日志必须显示：

```text
tol=128/450.0ms
```

仅看到 systemd 环境变量不算生效，必须检查新建 picoquic 连接的 `linkq` 日志。

## 4. 已落地的 picoquic 与发送路径修正

1. ACK-only 包在所有 loss detection 路径中均不计入有效 loss，也不向拥塞控制发送错误丢包信号；不再只覆盖连续 timer retransmit 特例。
2. BBR 长 RTT 路径的 `bw_lo/inflight_lo` 不再在同一 ProbeBW 周期内按 beta 每个 RTT 连续复合衰减。
3. app-limited startup 退出时保留近期有效带宽下限。
4. entry 和 middle 的下游 client 连接都支持调用 `picoquic_set_loss_reorder_tolerance()`。
5. latency 流的 route header 临时使用最高优先级，首部交给 QUIC 后立即恢复策略优先级。
6. FEC 保持观察模式，当前稳定基线不启用 source/repair 数据面。
7. entry 将 CUBIC 的 path cwin 和内部 `W_reno/W_max/previous_cwin/ssthresh` 都硬限制为 `512KiB`，spurious 恢复不能越过上限。
8. BBR 新增可选 `F` 参数；长 RTT 快速恢复时可按恢复前窗口比例设置下限，本线路仅 middle 使用 `F0.25`，exit 保持原行为。
9. 裸 IP TCP/443 在前 2 秒累计至少 `64KiB` 且平均上行超过 `256Kbps` 时立即提升为 media；其他未知流仍需连续高吞吐窗口确认。
10. 媒体 pacing bucket 限制为 `2 MTU`，重传同样受 pacing，普通 picoquic 连接保持原生行为。
11. 每条流记录 down/up/q2t 最老数据年龄；背压按 flow class 使用不同水位，不再统一允许积压 `2MB`。
12. ctrl 流持续两个 1 秒窗口超过 `128Kbps` 且累计超过 `64KB` 时自动降为 bulk；未分类上行持续超过 `256Kbps` 时提升为 media。
13. 连接级 ctrl token bucket 为 `1Mbps + 32KB burst`；媒体待发时超额 ctrl 临时从 `prio=2` 降为 `prio=6`，media 保持 `prio=4`，bulk 为 `prio=20`。
14. CUBIC 媒体连接的 repeat-loss 在一个有效 RTT 内最多减窗一次，并保留前一窗口 `50%` 下限；PTO/ECN 不受该保护，spurious 继续立即恢复。
15. event-loop 每 10 秒记录 busy max、wake late max、超过 `5ms/20ms` 次数；linkq 带 `run/worker/cid`，可按进程和连接隔离样本。
16. QUIC datagram 采用媒体优先和跨 session 轮询；本地队列项记录入队时间，媒体 UDP 超过 `200ms` deadline 后在进入 QUIC 或等待目标 DNS 阶段淘汰。

## 5. 历史单变量试验结论

| 试验 | 结果 | 产品化结论 |
|---|---|---|
| `NB_CC=cubic` | 部分窗口相对稳定，但仍出现红黄切换 | 保留为回退算法，不作为当前默认 |
| `NB_CC=fastcc` | 开播红色持续较久 | 不自动选择 |
| BBR + `Q0.0001:` | 配合 ACK/loss 修正后整体最好 | 当前默认 |
| 关闭 NB 自定义 UDP GSO | 早期单次测试曾出现连接中断；后续结合 pacing/CC 修正后的稳定基线为关闭 | 当前保持关闭，不能脱离整套基线单独解释早期结果 |
| 多连接池 | 多连接竞争使直播表现劣于纯 HY2 的可能性较高 | 当前固定单连接基线 |
| entry/middle 多 worker | middle 的共享 UDP 回包无法跨 picoquic context 分派 | middle 当前强制单 worker |
| 主动纠错 FEC | 早期版本出现延迟、卡顿和进程风险 | 完成模块化和矩阵验证前仅观察 |

## 6. 产品化自动开通是否可行

可以，但不能只执行 `ping` 或空闲 QUIC 握手后直接开通。推荐使用“静态检查 + 带负载预检 + 参数生成 + 小流量灰度 + 持续校准”五阶段流程。

### 6.1 阶段一：静态检查

- 校验证书、节点身份、系统时间和目标二进制哈希。
- 检查 UDP 端口、防火墙、MTU、socket buffer、CPU 和文件描述符上限。
- 确认数据面地址；存在 `private_ip` 时优先使用内网地址。
- 检查出口公网 IP 和 TikTok 白名单是否符合线路配置。

### 6.2 阶段二：带负载 QUIC 预检

每一跳独立运行至少 `90-180s`，流量模型应达到目标直播峰值的 `1.25倍`，并同时包含小控制流和持续媒体流。采集：

- RTT 的 min、P50、P95、P99 和 max。
- RTT variation 与 ACK delay。
- raw loss、effective loss、spurious loss 和 timer loss。
- reordering gap 和 reordering delay 的 P99/P99.9/max。
- delivery rate、pacing rate、cwin、bytes in flight 和 blocked 状态。
- CPU、事件循环延迟、socket drop 和发送队列水位。

探测样本不足 `10000` 个数据包时，不允许自动生成生产参数。

### 6.3 阶段三：生成线路参数

建议算法：

```text
reorder_gap = 向上取整(P99.9重排序包数 * 1.20)，限制在 3..256
reorder_delay = P99.9重排序延迟 + max(10ms, 0.25 * min_rtt)
reorder_delay 上限 = min(1000ms, 2 * 稳态RTT)
```

历史 KZ 样本曾达到约 `98包/345ms`；当前生产基线取更保守的 `128包/450ms`。后续不再把该固定值当作最终参数，而是以带负载探针得到的 P99.9 为输入，在灰度连接上验证后生成新版本。

其他决策：

- `effective_loss` 必须使用 `raw_loss - spurious_loss`，并过滤小样本窗口。
- FEC 只能在有效随机丢包持续超阈值且带宽余量足够时进入候选，不能因 raw loss 高直接开启。
- CC 不建议每条线路自动频繁切换；默认 BBR，CUBIC 仅作为经过同一矩阵验证的回退配置。
- worker 数由 CPU、包率和角色能力决定，不应由 RTT/loss 自动推导。
- 连接池大小属于架构容量参数，不应在单次线路探测后自动扩大。

### 6.4 阶段四：灰度开通

- 先用一个测试账号或 `1%-5%` 流量运行 `10-15分钟`。
- 检查首字节 P95、持续码率、spurious ratio、直播状态和观看端延迟。
- 灰度失败立即回退上一份已签名线路配置，不现场连续试多个变量。
- 灰度通过后再提升到全量。

### 6.5 阶段五：运行期校准

运行期可以自动调整 reorder tolerance，但必须满足：

- 使用滑动窗口和迟滞，至少连续多个有效窗口才升档或降档。
- 升档速度可以快，降档必须慢，避免参数抖动。
- 每次只调整 gap 或 delay 中的一个变量并记录版本。
- 参数变化要求新建 QUIC 连接生效，旧连接不原地修改。
- 不自动开启主动 FEC；FEC 需要独立的 canary 和完整性指标。

## 7. 控制面需要补齐的能力

当前已经提供 `tools/line_probe.py`，它采集每跳 ICMP 与运行中 QUIC linkq，生成 `build/line-profile-candidate.json`。当前实现只读，不会直接修改线上配置：

```powershell
python tools/line_probe.py --ping-samples 30 --target-mbps 10
```

主动模式通过现有 SOCKS 用户认证和节点证书认证进入真实三跳主链。它先访问内部 `nb-probe-echo.internal:9` 做 payload 完整性校验，再访问 `nb-probe-sink.internal:9` 按目标码率发送数据；exit 不访问公网，只返回接收字节数。采样从探针开始前的日志字节偏移起算，不混入历史窗口：

```powershell
$env:NB_SOCKS_USERNAME = "<探针账号>"
$env:NB_SOCKS_PASSWORD = "<探针密码>"
python tools/line_probe.py --active --duration 90 --target-mbps 10
```

开通可售套餐时不再直接把探针速率等同于套餐速率。使用 `--package-mbps` 后，
默认按套餐的 `1.25` 倍做容量资格测试。例如 5M、10M、15M 分别要求探针目标达到
6.25、12.5、18.75 Mbps；稳定配置还要求实测速率至少达到该资格速率的 `95%`。
线路只能勉强达到标称套餐时拒绝开通，不能把全部容量售出：

```powershell
python tools/line_probe.py --active --duration 90 --package-mbps 15 --headroom-ratio 1.25
```

批量开线使用 `tools/line_provision.py`。清单格式参考
`tools/line-provision.example.json`，每条线路独立指定拓扑、基线 profile、套餐、SOCKS
端口、用户名和客户端密码环境变量。工具按清单顺序执行真实三跳 QUIC 探针，避免并发探针
互相争抢带宽；单条失败不会阻止后续线路采样，但整批命令最终返回失败：

```powershell
$env:NB_CLIENT_PASSWORD_KZ_01 = "<客户端密码>"
python tools/line_provision.py tools/line-provision.example.json
```

每条通过准入的线路生成以下文件：

- `probe-candidate.json`：原始主动探针和每跳证据。
- `stable-profile.json`：状态为 `stable-qualified` 的版本化线路参数，尚未灰度前不是线上 active 基线。
- `deployment-hosts.json`：已注入 entry/middle 传输推荐值的部署拓扑。
- `tenant-route-policy.json`：按线路换算的上/下行平均 `rate_up_kbps`、`rate_down_kbps`，分别配套峰值窗口并固定出口路由；旧 `rate_kbps` 策略继续按双向同值读取。
- `client.json`：SOCKS5/Shadowrocket 客户端信息；该文件按私密文件写入，批次汇总不记录密码。

多线路支持的是一份清单中的多个独立线路实例，通常对应不同三节点拓扑或不同 entry
监听实例。当前 `nb-entry.service` 单实例仍只能绑定一个 SOCKS 端口；同一 entry 上同时开多个
端口需要后续服务实例化（例如 `nb-entry@<line_id>.service`），不能仅生成两个配置就视为已部署。

### 7.1 仅提供三台机器时的一键开线

`tools/line_open.py` 将三机清单转换为完整 NB 拓扑，并串联首次开线所需的全部阶段。
清单可以直接使用现有 `entry/middle/exit` 格式，也支持 `machines[]`（示例见
`tools/three-hosts.example.json`）以及旧的 `edges/relays/terminals` 格式。密码字段优先使用
`password_env`；兼容读取清单中的 `password`，但生成的拓扑会剥离明文密码。

默认调用只生成计划，不连接服务器：

```powershell
python tools/line_open.py tools/lab-hosts.json `
  --line-id gz-hk-kz-15m-01 --package-mbps 15 --socks-port 1080
```

确认 `build/line-open/gz-hk-kz-15m-01/plan.json`、三机角色和 middle 内网地址后执行：

```powershell
$env:NB_SSH_PASSWORD_ENTRY = "<entry SSH 密码>"
$env:NB_SSH_PASSWORD_MIDDLE = "<middle SSH 密码>"
$env:NB_SSH_PASSWORD_EXIT = "<exit SSH 密码>"
$env:NB_CLIENT_PASSWORD = "<可选；不设置则自动生成>"

python tools/line_open.py tools/lab-hosts.json `
  --line-id gz-hk-kz-15m-01 --package-mbps 15 --socks-port 1080 --execute
```

执行顺序固定为：生成独立节点证书、首次固定 SSH 主机密钥、构建并部署保守基线、
真实三跳 QUIC 容量探针、生成稳定配置、重新构建部署、签名下发租户/固定出口策略、
输出 `client.json`。探针或部署任何一步失败都会终止后续阶段；失败时保留基线和证据，
不会生成已开通结论。执行机需要 Python、Paramiko 和 OpenSSL。

探针输出 schema v2 同时包含 MTU 证据。每一段线路使用 IPv4 DF ICMP 二分探测路径 IP MTU，
并从有效负载窗口的 `linkq mtu=` 读取 picoquic 已实际发送成功的 QUIC UDP payload 上限。
推荐的 `mtu_max` 是 IP 层上限，不是 QUIC payload：DF 结果默认预留 48 字节安全余量，
运行中 QUIC 已验证值按 `payload + 28` 换算。ICMP 被禁或样本不足时只降低置信度并保留当前配置，
不得仅凭一次 ICMP 结果自动覆盖线上 MTU。

主动探针仍只生成 candidate，`auto_apply_allowed` 保持 `false`。参数矩阵灰度、签名审批和自动回滚完成前，不得直接修改生产线路。

当有效 QUIC 样本不足 `10000` 包或 6 个负载窗口时，结果标记为 `insufficient-load`，禁止自动应用。机器可读的当前基线默认保存在本地 `build/line-profiles/active.json`，也可通过 `NB_LINE_PROFILE_FILE` 指定；该目录不进入版本控制。

当前能力属于“静态连通性 + 运行期被动样本探针”，现在即可用于开线前检查和候选参数记录；它还不是无人值守自动开通器。只有补齐独立 QUIC 负载发生器、灰度会话、配置签名与自动回滚后，才允许把 `auto_apply_allowed` 置为 `true`。

产品化自动化仍需完成：

1. 将 `NB_CC`、BBR options、reorder 参数、GSO、worker 和连接池从部署脚本/编译常量迁移到版本化线路配置。
2. 将当前 ICMP+运行指标探针扩展为独立 QUIC 负载发生器，不依赖业务流量积累样本。
3. 建立线路配置签名、审批、灰度比例、回滚版本和审计记录。
4. 建立参数生效回读；控制面下发值必须与 `linkq tol/cc` 实际值一致。
5. 为真实丢包、伪丢包、重排序、队列等待和直播业务状态建立统一时间线。

## 8. 当前结论

产品化时可以先自动测试线路，再生成参数并开通，但必须以带负载 QUIC 探测和灰度验证为前提。可以在开通前可靠确定的主要是地址、MTU、RTT、ACK、重排序容忍度和基础 socket 参数；CC、FEC、连接池与 worker 不能仅根据一次线路测试自动决定。

2026-07-20 上午 KZ 当前基线已连续直播 37 分钟未出现状态抖动。该结果只证明当前设备、当前时间窗和当前业务负载下通过阶段性稳定性验证；历史上下午时段更容易不稳定，因此还必须在下午窗口复测，并同时记录直播端状态、观看端卡顿、清晰度和端到端延迟，不能据此直接宣布产品化完成。

北京时间 2026-07-20 17:29，美国线路开始变黄并持续到 17:30 下播。该测试拓扑为广州 `106.75.134.170`→香港 `152.32.187.37`→美国出口 `154.44.88.184`，不是 KZ 线路，不能归入 KZ 的参数校准或 P0 canary 结论。

2026-07-21 已按 UTC `09:15–09:32` 补取 entry 和 exit 历史日志。黄灯开始时 entry→middle 的 RTT 约 10.5 ms、抖动 0.1–0.4 ms、有效丢包 0%，事件循环没有超过 5 ms 的停顿；美国 exit 到 TikTok RTC 目标的 TCP 建连约 1 ms，相关短会话正常完成。因此没有证据表明 `17:29` 黄灯由当时的 NB QUIC 拥塞、队列或美国出口建连失败直接触发。

同一窗口从至少 `17:15` 开始没有观察到持续的视频上行码率。`17:29` 附近已分类的 webcast、frontier 和 UDP 50001/50020 流大多只有 0–数 Kbps，最高持续流约 23 Kbps；队列和队龄接近 0。该事实更符合“视频媒体没有经过 NB、客户端 UDP 旁路，或 TikTok 在黄灯前已经停止媒体发送”，而不是 NB 承载视频后发生排队。仅凭本次日志无法在这三种情况中唯一确定，需要下一次测试同时记录 UDP_ASSOCIATE、目标五元组和手机侧上行字节。

## 9. 固定出口下的动态选路

第二阶段控制面采用“固定出口、入口与中继可变”的有向图：

- `exit` 是线路合同与公网身份锚点，不参与自动切换。
- `entry` 可以来自不同地区、运营商或用户接入点。
- `middle` 可以为零个、一个或多个候选中继，但 V1.5 数据面仍按三跳执行。
- 每条边独立保存探针结果、配置版本、容量、成本和健康状态。

选路分为两步。先做硬性淘汰：认证失败、出口不可达、MTU 不合格、有效丢包或队列超过阈值、容量不足的路径不得进入评分。剩余路径按以下维度评分：

```text
score = 0.30 * RTT_P95
      + 0.20 * jitter_P95
      + 0.25 * effective_loss_penalty
      + 0.15 * queue_penalty
      + 0.10 * cost_penalty
```

评分必须按媒体方向和控制方向分别计算。切换采用迟滞：候选路径连续多个窗口优于当前路径且改善超过阈值，才允许成为新会话路径。已建立的直播会话保持原路径，只有新会话切换；除非当前路径失效，不在直播过程中直接迁移全部流。

建议控制面数据模型：

```json
{
  "fixed_exit": "kz-1",
  "candidate_entries": ["gz-83", "sz-02", "bj-01"],
  "candidate_relays": ["hk-216", "jp-03", "sg-02"],
  "active_path": ["gz-83", "hk-216", "kz-1"],
  "switch_policy": {
    "new_sessions_only": true,
    "minimum_improvement_pct": 15,
    "healthy_windows": 6,
    "failure_windows": 3
  }
}
```
